## Doubts and choices to review

- **Per-partition automatic failover (Cosmos DB)**: `cosmos-failover-options` (answer) and `cosmos-outage-statements` (stem line) use it as the reliability page describes it (single write region, recovery in about three minutes, no manual action, works with non-strong consistency). The fetch did not show a preview label; confirm its general availability before publication. The course chapter 32 does not mention it.
- **Failover groups with several secondaries** are in preview for Azure SQL Database (up to four secondary servers). No question relies on "one secondary only"; the failover group / active geo-replication distinction rests on the stable listener endpoint and group failover.
- **Statements from general knowledge, not read on a fetched page**: MySQL flexible server read replicas are asynchronous and promoted manually (`mysql-zone-redundant-ha`, distractor c); log shipping runs on a schedule with a manual switch (`sqlvm-ag-zones`, distractor c); an availability group fails over automatically without shared storage (`sqlvm-ag-zones`); savings plan and Reserved Instances terms (`capacity-reservation`, distractors; the reservation page confirms the Reserved Instances part).
- **SLA figures used**: PostgreSQL flexible server 99.9 / 99.95 / 99.99 % (reliability page). No VM, App Service, SQL or Cosmos DB percentage is quoted, since Learn sends to the SLA document. The 99.99 % of VMs across zones appears on the scale set zones page and the SQL VM HADR page but is not used as a deciding fact.
- **Site Recovery zone-to-zone**: the fetch summary reported an RTO "up to one hour"; not used. `zone-ha-or-zone-dr` states that the VM uses LRS disks because zone-to-zone replication does not support ZRS disks.
- **Azure Files**: with the provisioned v2 model, HDD shares can also live in FileStorage accounts, so `files-ssd-zone` and `storage-redundancy-match` speak of "SSD file share" / "HDD file share" and never tie the redundancy to the account kind.
- **Hyperscale zone redundancy**: accepted backup storage is zone-redundant or geo-zone-redundant; `hyperscale-zone-redundancy` treats geo-redundant (GRS) backup storage as not accepted, as the page says.
- **Profile vs task**: the profile says AZ-305 has no step ordering; the task asks for one `ordering` (`storage-failover-sequence`, Last Sync Time → unplanned failover → back to GRS) and one `hotarea` (`sqldb-config-hotarea`).
- **Overlap inside the batch**: ZRS is the answer of `storage-zone-residency` (blobs, data residency) and of `files-ssd-zone` (SSD file shares support LRS and ZRS only); the decisions differ.
