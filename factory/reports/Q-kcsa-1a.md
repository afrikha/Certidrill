## Doubts and choices
1. **4Cs reference**: the 4Cs page exists only in archived docs (`v1-28.docs.kubernetes.io`, not an accepted host). The GitHub copy (`github.com/kubernetes/website/blob/release-1.28/.../security/overview.md`) could not be fetched (GitHub access blocked in this session); I read the raw file on raw.githubusercontent.com (not an accepted host) to check the layer contents. The 4Cs questions (1.1.1, 1.1.2) therefore cite "Cloud Native Security and Kubernetes" and the Security Checklist, which cover the same controls but not the 4Cs names. A reviewer may want to add the GitHub release-1.28 page as a reference if it can be fetched.
2. **Layer mapping** follows the archived 4Cs page and chapter 11 (network access to API server/nodes/etcd and cloud API least privilege = Cloud; dependency scanning, ports, DAST = Code). I avoided the ambiguous cases (etcd encryption, mTLS).
3. **Shared responsibility (1.2.1)**: no kubernetes.io page covers it; the whitepaper only names the model. The questions state generic splits (provider operates a managed control plane; RBAC/workloads always the customer's) and avoid worker-node responsibilities of managed services, which vary. `kcsa-1a-shared-resp-managed-visibility` says managed control plane components "usually" don't appear as inspectable Pods (general knowledge).
4. **Per-workload cloud identity** (`kcsa-1a-infra-per-workload-identity`): "most managed services map a ServiceAccount to a cloud identity" is from general knowledge (as in chapter 12), not a fetched page.
5. **Node administrative access** (`kcsa-1a-node-admin-access`): bastion/session logging is general practice; the cited pages only support short-lived credentials, rotation and minimal admin access.
6. kube-proxy port and the NodePort range were not visible in the fetched part of Ports and Protocols; no question depends on their values (kube-proxy is only said not to use 10250).
7. MITRE ATT&CK tactic names not used anywhere. PodSecurityPolicy not used.
