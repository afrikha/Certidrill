## Facts to keep in mind

- GitHub `concurrency` now has a `queue: max` option (up to 100 pending runs). With the default `queue: single`, a newer pending run replaces the older pending one. gh-concurrency only requires "never two at once, never cancel the running one", so this doesn't change the answer.
- Azure DevOps public projects are retired (they become private in 2027). No question relies on public-project limits.
- Exclusive lock: Learn says `runLatest` is the default `lockBehavior` (cab-latest, sequential-lock).
- Delay@1: agentless jobs time out after 60 minutes by default, so a 120-minute delay also needs a higher job timeout (server-delay).

## Doubts

- vm-strategies: the "Manage VM resources in environments" page says VM resources support runOnce and rolling. No page says explicitly that canary is rejected for VM resources. The question asks which strategies are supported and gives canary as the wrong answer.
- Learn's Expressions page is inconsistent about stage-level conditions: its table shows `stageDependencies.<stage>.outputs[...]`, but its example and prose use `dependencies.<stage>.outputs['job.step.var']`. stage-output-condition uses the `dependencies` form as the answer. Its stage-level distractors (key without the job name, job-level `dependencies`, `variables[...]`) are wrong under either reading.
- check-order treats approval categories as the Learn page describes them. No approval is configured in that scenario.
