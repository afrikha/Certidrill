## Choices and doubts
- Maximum number of HPK levels is not tested: the main HPK page and limits page say 3, the
  "unlimited scale" page says up to 4 when `enableHierarchicalPartitionKeyIdLastLevel` is set.
- Python HPK code is based on the `PartitionKey` class reference (`path` list, `kind="MultiHash"`) and the
  `read_item`/`query_items` signatures (`partition_key` accepts a sequence); the Python tab of the HPK page could not be read.
  `"Range"` is used as a wrong `kind` option (exists in the REST API PartitionKind enum, not checked in the Python SDK).
- Preview features left out of answers: global secondary indexes, delete by partition key, throughput redistribution,
  throughput buckets. Stored procedures and triggers (no longer in the skills list) are not used as answers;
  same-partition atomicity is done with transactional batch.
- KQL distractors (`CDBPartitionKeyStatistics`, `CDBQueryRuntimeStatistics`, `AzureMetrics`, columns `SizeKb`,
  `DurationMs`, `ResponseLength`) are real Cosmos DB / Azure Monitor names but their pages were not fetched
  (WebFetch budget ran out near the end); the change feed overview page was not fetched either — change feed
  denormalization is referenced through model-partition-example.
- Course chapter `13-data-models-partitioning` did not exist while writing: check that its decision tables agree
  (20 GB / 10,000 RU/s per logical partition, 50 GB per physical partition, even RU split across physical partitions,
  HPK prefix routing, random vs precalculated suffix).
