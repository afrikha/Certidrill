# QZ-ai-300-31-foundry-environments — notes

## Chapter vs current Learn (to fix in the chapter, not done here)

- **Azure AI Search renamed.** Learn now names the service **Foundry IQ (Azure AI Search)**. Its overview page title is "Introduction to Foundry IQ (Azure AI Search)". The Foundry pages (network isolation, standard setup, create projects, Agent Service private networking) write "Foundry IQ" or "Foundry IQ (Azure AI Search)". The chapter (and the mock bank) still write "Azure AI Search" everywhere. In the network isolation page, the trusted services table lists **Foundry Tools** (`Microsoft.CognitiveServices`), **Foundry IQ** (`Microsoft.Search`) and **Azure Machine Learning**. The quiz uses "Foundry IQ (Azure AI Search)" in q8.
- **Browser automation with network injection.** The chapter's tool table says "Not supported". The current matrix on "How to configure network isolation for Microsoft Foundry" says **Supported, through your VNet subnet in Playwright Workspaces**. "Network isolation for a toolbox in Microsoft Foundry" still says "Not supported". Learn contradicts itself here, so the quiz doesn't use browser automation. The same matrix adds Fabric IQ (partial, via MCP) and Fabric Data Agent (not supported).
- **Default project features.** The chapter says that only the default project supports "fine-tuning". "Create a project for Microsoft Foundry" is more precise. OpenAI fine-tuning and Speech fine-tuning are default-only, but **Language fine-tuning** is available in the other projects too. q5 tests only Responses, Batch and stored completions.
- **Reserved address ranges.** The chapter mentions only `172.17.0.0/16`, which comes from the private link page (Docker bridge). The Agent Service private networking page lists other ranges for the agent subnet that must not overlap with the VNet or with peered VNets: `169.254.0.0/16`, `172.30.0.0/16`, `172.31.0.0/16`, `192.0.2.0/24`, `0.0.0.0/8`, `127.0.0.0/8` and three `100.100.x` ranges. For hosted agents, private endpoint addresses must avoid `192.168.0.0/24`. The same page says that one agent subnet can't be shared between Foundry resources and suggests `/24` for production. It also requires the Foundry resource to be in the same region as the VNet.
- **Microsoft-managed network** (`networkInjections.useMicrosoftManagedNetwork`, `az cognitiveservices account managed-network` in preview): not found on the Agent Service private networking page I fetched. It's in preview according to the chapter itself. It isn't tested.
- **Automatic role assignments.** The RBAC page also says that creating a project in the Foundry portal adds role assignments for the user **and for the project's managed identity** if the creator can assign roles. The chapter covers only the automatic assignment at resource creation.
- **Deletion order (missing from the chapter).** With private networking, delete the Foundry resource and the VNet last, and purge the Foundry resource before you delete the VNet (Agent Service private networking page).

## Verified and used

- Default project after deletion (q1), Reader on the resource plus Foundry User on the project for developers (q2), Owner/Contributor without data actions and Azure AI Developer not applying to Foundry projects (q6): "Role-based access control for Microsoft Foundry" and "Create a project for Microsoft Foundry".
- Removing private endpoints doesn't make the resource public, enabling public access keeps the private endpoints, selected networks with IP rules, and on-premises access (q3, q7): network isolation page. For q7, the DNS forwarder in the linked VNet is described in "Azure Private Endpoint DNS Integration Scenarios" ("DNS queries for private endpoints must originate from the virtual network that is linked to the private DNS zone"). That page doesn't state explicitly that 168.63.129.16 can't be reached from on-premises. The explanation of option b rests on the sentence above.
- `az cognitiveservices account project create`: `--location` is required (the chapter's example includes it). `--user-assigned-identity` takes the resource ID, and `--assign-identity` used with it also adds a system-assigned identity. Without `--user-assigned-identity`, a system-assigned identity is used (CLI reference). The chapter's example passes `--assign-identity` alone, which still works. Its description is slightly misleading, though: the flag matters only together with `--user-assigned-identity`.
- Capability settings can't be updated on an existing project, so the project has to be deleted and recreated (Agent Service private networking page). Managed identity lifecycles come from "What is managed identities for Azure resources?" (q10).
- `uniqueString` is deterministic and not globally unique ("Bicep functions - string"). The naming rule (globally unique, 2–64 lowercase letters, digits and hyphens) is the sample template's `AccountNameInvalid` rule in the Bicep quickstart (q9).
