Analytics questions start once the data has landed in AWS: store it in a data lake, catalog it, secure it, transform it into an efficient format, then query and visualize it. The answer is usually the serverless, managed option that meets the requirement with the least operational overhead, unless the scenario needs a specific framework, very large clusters or fine-grained control.

## Analytics and visualization services

| Service | What it does | Choose it when |
| --- | --- | --- |
| Amazon Athena | Serverless interactive SQL directly on data in S3, using tables of the AWS Glue Data Catalog; also runs Apache Spark; you pay for the queries you run | Ad hoc SQL on S3 with no infrastructure, log analysis, querying a data lake |
| AWS Lake Formation | Central governance of a data lake: fine-grained permissions on Data Catalog databases, tables, columns, rows and cells, enforced across Athena, Redshift Spectrum, EMR, Glue and Quick | Several teams or accounts share a data lake with column-, row- or tag-based access |
| Amazon Quick | AI-powered service whose Quick Sight capability (formerly Amazon QuickSight) provides BI dashboards, embedded analytics and the SPICE in-memory engine | Business users need interactive dashboards on Athena, Redshift or other sources |
| Amazon Redshift | Data warehouse (provisioned or Serverless); Redshift Spectrum queries data in S3 | Complex SQL with many joins over large structured data, consolidated from many sources and kept for long periods |
| Amazon EMR | Managed big data frameworks (Spark, Hadoop, Hive, Presto, HBase, Flink) | Custom code on very large data sets, existing Hadoop or Spark jobs |
| AWS Glue | Serverless data integration: Data Catalog, crawlers, Spark ETL jobs | Cataloging and transforming data without managing clusters |
| Amazon OpenSearch Service | Search and log analytics with OpenSearch Dashboards | Full-text search, log and clickstream exploration |
| AWS Data Exchange | Subscribe to third-party data sets | External data feeds into the lake |

> **Exam trap.** Athena is for interactive, ad hoc queries; Redshift is for a warehouse with heavy, repeated, join-intensive queries. "Query CSV files in S3 occasionally with SQL, least operational overhead" is Athena, not Redshift or an EMR cluster.

<!-- section: glue-transformation | objectives: 3.5.4 -->
## Data transformation with AWS Glue

| Component | Role |
| --- | --- |
| Data Catalog | Central metadata store (databases, tables, schemas, partitions) used by Athena, EMR, Redshift Spectrum and Glue jobs |
| Crawlers | Scan S3, JDBC and other sources, infer schemas and create or update catalog tables and partitions; run on demand or on a schedule |
| ETL jobs | Serverless Apache Spark jobs (written in a script or generated by AWS Glue Studio's visual editor); batch or streaming ETL |
| Job bookmarks | Keep track of data already processed so a recurring job reads only new files |
| Triggers and workflows | Start crawlers and jobs on a schedule, on demand or on an event, and chain them |
| AWS Glue DataBrew | Visual, no-code data preparation for analysts |
| FindMatches | Machine learning transform that finds duplicate records |

Choosing a transformation engine:

| Requirement | Answer |
| --- | --- |
| Serverless ETL on S3 data, Spark without clusters | AWS Glue job |
| Analysts clean data visually, no code | AWS Glue DataBrew |
| Small per-file transformation when an object arrives | Lambda on an S3 event (minutes, not hours, per invocation) |
| Existing Spark or Hadoop code with specific versions or tuning | Amazon EMR |
| SQL-only reshaping of tables already in the catalog | Athena `CREATE TABLE AS SELECT` |
| Continuous transformation of a stream | Glue streaming ETL or Managed Service for Apache Flink |

> **Exam tip.** "Process only the files added since the last run" is a Glue job with job bookmarks enabled; "keep the catalog updated when new partitions arrive" is a scheduled crawler, or partition projection in Athena.

## Building and securing data lakes

A data lake on AWS is S3 (storage), the Glue Data Catalog (metadata) and Lake Formation (governance):

1. Create S3 buckets or prefixes for zones: raw (as ingested), processed (cleaned, Parquet), curated (business-ready).
2. Register the S3 locations with Lake Formation and name data lake administrators.
3. Catalog the data with crawlers or Glue jobs.
4. Grant permissions with Lake Formation instead of per-bucket IAM policies.
5. Query with Athena, Redshift Spectrum, EMR or Quick; every engine enforces the same grants.

Lake Formation permissions:

| Feature | Use |
| --- | --- |
| Grant and revoke | Database, table and column permissions, like a relational database |
| Data filters | Row-level and cell-level security, for example hide PII columns and rows of other countries |
| LF-Tags | Tag-based access control: tag databases, tables or columns (`confidentiality=high`) and grant on tags; scales to thousands of resources |
| Cross-account sharing | Share catalog resources with other accounts, organizational units or principals |
| Hybrid access mode | Adopt Lake Formation permissions incrementally while existing IAM-based access keeps working |

Storage security for the lake: S3 Block Public Access, default encryption with SSE-KMS (key policies control who can decrypt), bucket policies requiring TLS and VPC endpoints, versioning, CloudTrail data events for auditing, and Amazon Macie to discover sensitive data in the buckets.

> **Exam trap.** IAM policies and bucket policies work at object and prefix level: they can't hide one column of a table. "Analysts may query the table but must not see the `ssn` column" is a Lake Formation column permission or data filter.

## Visualization strategies

| Requirement | Answer |
| --- | --- |
| Interactive business dashboards shared with many users, embedded in an application | Quick Sight in Amazon Quick |
| Fast dashboards without querying the source each time | Import the data into SPICE (in-memory engine), refreshed on a schedule; reused without additional per-query charges at the source |
| Always-current data from the source | Direct query to Athena, Redshift or a database |
| Log, search and clickstream exploration | OpenSearch Dashboards on Amazon OpenSearch Service |
| Operational metrics from Prometheus, CloudWatch and other sources | Amazon Managed Grafana |
| Resource and application metrics for operators | CloudWatch dashboards |

SPICE capacity is allocated per Region and shared by the users of the account in that Region. A common serverless analytics chain is S3 (Parquet) → Glue Data Catalog → Athena → Quick Sight.

> **Exam tip.** When the source charges per query (Athena scans) and many users open the same dashboard, SPICE reduces both latency and cost: the source is queried only when the dataset is created or refreshed.

## Compute options for data processing

| Option | Characteristics | Fits |
| --- | --- | --- |
| Amazon EMR on EC2 | Cluster of primary, core and task nodes; you choose instance types and framework versions | Large, long-running or heavily tuned Spark, Hive, HBase, Presto workloads |
| Amazon EMR on EKS | EMR jobs on an existing Amazon EKS cluster | Teams that already run Kubernetes and want shared infrastructure |
| Amazon EMR Serverless | Spark and Hive applications with no cluster to configure; resources allocated per job and released after; optional pre-initialized capacity for fast start | Intermittent jobs, no cluster operations |
| AWS Glue | Serverless Spark ETL integrated with the Data Catalog | ETL and catalog-driven pipelines |
| Athena | Serverless SQL and Spark | SQL-based transformation and analysis |
| Amazon Redshift | Massively parallel SQL warehouse | Transformations inside the warehouse (ELT) |
| AWS Lambda | Event-driven functions, up to 30 minutes on the current Lambda quotas page (older pages and the FAQ still say 15 minutes; 90 minutes for some Lambda Managed Instances invocations) | Small files, per-event processing |
| AWS Batch | Managed batch scheduling on EC2 or Fargate, including Spot | Containerized batch jobs that are not Spark |

EMR on EC2 details:

- **Core nodes** run tasks and store HDFS data; **task nodes** only run tasks, so they are the safe place for **Spot Instances**. EMR keeps YARN application masters on core nodes for that reason.
- **HDFS is ephemeral**: it disappears with the cluster. Keep input and output in S3 (EMRFS or the S3A connector) and use HDFS for intermediate data.
- **Transient clusters** start, run their steps and terminate, so you pay only while processing; long-running clusters suit interactive or continuous use. EMR managed scaling adjusts the cluster to the load.

> **Exam trap.** Running core nodes on Spot risks HDFS data loss when instances are reclaimed. "Lowest cost, fault-tolerant processing on EMR" is On-Demand (or Reserved) primary and core nodes with task nodes on Spot, data in S3.

## Transforming data between formats

Row-oriented text formats (CSV, JSON) are easy to produce but expensive to query: every query reads every column. Columnar formats (Apache Parquet, Apache ORC) store data by column, compress well and let engines read only the columns and row groups they need, so Athena scans fewer bytes and costs less.

| Method | When |
| --- | --- |
| AWS Glue ETL job (Spark) reading the CSV catalog table and writing Parquet partitioned by date | Recurring, large conversions, with job bookmarks for new files |
| Athena `CREATE TABLE AS SELECT` (CTAS) or `INSERT INTO` | SQL-only conversion, no job to manage |
| Data Firehose record format conversion | Streaming JSON converted to Parquet or ORC before it lands in S3 (CSV needs a Lambda transformation to JSON first) |
| EMR Spark job | Very large or custom conversions in an existing EMR environment |

```text
CREATE TABLE curated.sales_parquet
WITH (
  format = 'PARQUET',
  write_compression = 'SNAPPY',
  external_location = 's3://example-lake-curated/sales/',
  partitioned_by = ARRAY['sale_date']
) AS
SELECT order_id, store_id, amount, sale_date
FROM raw.sales_csv;
```

Combine the format with **partitioning** (prefixes such as `sale_date=2026-11-19/`, used in `WHERE` clauses), **compression** (Snappy, ZSTD, GZIP) and reasonably large files (avoid millions of small files). Partition projection lets Athena compute partitions from table properties instead of loading them into the catalog.

> **Exam tip.** "Reduce Athena query cost and improve performance" without changing the queries' results: convert to compressed Parquet and partition by the column used in filters.

<!-- section: key-points -->
## Key points

- Athena: serverless SQL on S3, pay per query. Redshift: warehouse for heavy joins. EMR: frameworks and custom code. Glue: serverless ETL and the Data Catalog.
- Lake Formation adds database, table, column, row and cell permissions, LF-Tags and cross-account sharing on top of S3 and the catalog.
- Quick Sight (Amazon Quick) for BI dashboards; SPICE for fast, reusable data; OpenSearch Dashboards for logs; Managed Grafana for operational metrics.
- EMR: Spot on task nodes, data in S3, transient clusters; EMR Serverless for no cluster management.
- CSV to Parquet with Glue, Athena CTAS or Firehose (JSON input); partition and compress.
