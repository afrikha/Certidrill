An artifact is anything a pipeline produces and later deploys or reuses: a .zip bundle, a JAR or npm package, a container image, an AMI, a packaged CloudFormation template, a test report or an SBOM. Artifact questions test how to build it once and promote the same bytes through every environment, how to store it in the right repository with the right permissions and encryption, how to prove its integrity, how to clean up old versions without breaking deployments, and how to automate AMI and container image builds. This chapter covers artifact use cases and security, creation methods, lifecycle, CodeArtifact, ECR and S3 repositories, build tool configuration and EC2 Image Builder.

## Artifact use cases and secure management

| Artifact | Typical repository | Deployed by |
| --- | --- | --- |
| Application bundle (.zip with an appspec) | Amazon S3 | CodeDeploy, Elastic Beanstalk |
| Library or package (Maven, npm, PyPI, NuGet) | AWS CodeArtifact | Build tools of other projects |
| Container image | Amazon ECR | ECS, EKS, Lambda container functions |
| Lambda .zip package or layer | Amazon S3 | CloudFormation, SAM, Lambda API |
| AMI | EC2 (EBS snapshots) | Launch templates, Auto Scaling groups |
| Packaged template and assets | Amazon S3, Amazon ECR | CloudFormation, CDK |
| Reports and SBOMs | S3, CodeBuild report groups | Auditors, security tools |

The governing principle is **build once, deploy many**: the artifact tested in staging is the one deployed to production, identified by an immutable version (commit SHA, semantic version, image digest), with environment-specific configuration injected at deployment time. Rebuilding per environment breaks traceability and can ship untested bytes.

Securing artifacts covers five controls:

| Control | How on AWS |
| --- | --- |
| Immutability | ECR tag immutability (`IMMUTABLE`, or `IMMUTABLE_WITH_EXCLUSION` for tags such as `latest`); S3 versioning and Object Lock; CodeArtifact versions that cannot be republished unless deleted |
| Integrity and provenance | AWS Signer: Lambda code signing for .zip packages and layers, ECR managed signing of images on push (or the Notation CLI with the AWS Signer plugin); SBOMs |
| Encryption | KMS on the S3 artifact bucket, ECR repositories (AES-256 by default, KMS optional) and the CodeArtifact domain |
| Access control | Repository and bucket policies, IAM roles per pipeline and per environment, VPC endpoints so builds reach repositories privately |
| Vulnerability and supply chain | ECR enhanced scanning with Amazon Inspector; CodeArtifact package origin controls against dependency substitution |

Lambda code signing uses a **code signing configuration** that lists allowed AWS Signer signing profiles. Lambda checks integrity, expiry, profile mismatch and revocation at deployment time. With `UntrustedArtifactOnDeployment` set to `Warn` (default) the deployment proceeds with a warning; with `Enforce` it is blocked. Code already running is not affected until the next deployment.

> **Exam trap.** "Ensure that only code built by the approved pipeline runs in production Lambda functions" is code signing with `Enforce`, not an IAM condition on the S3 bucket or a scan. "Prevent a public package with the same name as an internal package from being pulled in" is CodeArtifact package origin controls: a package first published internally gets Publish `ALLOW` and Upstream `BLOCK`.

## Methods to create and generate artifacts

| Artifact | How it is generated |
| --- | --- |
| Compiled package or bundle | Build tool in CodeBuild (`mvn package`, `npm run build`, `dotnet publish`); the buildspec `artifacts` section zips the output to S3 |
| Package published for reuse | `mvn deploy`, `npm publish`, `twine upload` or `dotnet nuget push` to CodeArtifact after `aws codeartifact login` |
| Container image | `docker build` and `docker push` in CodeBuild with privileged mode; the CodePipeline `ECRBuildAndPublish` action; an EC2 Image Builder container recipe |
| Serverless application | `sam build` then `sam package` (or `aws cloudformation package`): local code is uploaded to S3 and the template is rewritten with the S3 locations |
| CDK application | `cdk synth` produces the cloud assembly (templates and asset manifests); assets are published to the bootstrap bucket and ECR repository |
| AMI | EC2 Image Builder image pipeline, or an SSM Automation runbook such as `AWS-UpdateLinuxAmi` |
| Deployment descriptors | Files generated by the build: `imagedefinitions.json` for the ECS standard deploy action, `appspec.yaml` and `taskdef.json` for ECS blue/green through CodeDeploy |

Version every artifact from the source: the build reads `CODEBUILD_RESOLVED_SOURCE_VERSION` (the commit ID) or a Git tag and uses it as image tag, package version or S3 key, so any running version can be traced back to its commit.

```bash
REPO=111122223333.dkr.ecr.eu-west-1.amazonaws.com/orders-api
TAG=$(echo "$CODEBUILD_RESOLVED_SOURCE_VERSION" | cut -c 1-12)
aws ecr get-login-password --region eu-west-1 | docker login --username AWS --password-stdin 111122223333.dkr.ecr.eu-west-1.amazonaws.com
docker build -t "$REPO:$TAG" .
docker push "$REPO:$TAG"
printf '[{"name":"api","imageUri":"%s"}]' "$REPO:$TAG" > imagedefinitions.json
```

> **Exam tip.** When an option rebuilds the application in each environment's pipeline stage, it fails "deploy exactly what was tested". The correct option builds once, stores the artifact, and has later stages deploy that same version.

## Artifact lifecycle considerations

An artifact goes through **create → store → scan → promote → deploy → retain → retire**. Lifecycle questions ask how to keep what is needed for rollback and audit and delete the rest automatically.

| Repository | Lifecycle mechanism |
| --- | --- |
| Amazon ECR | Lifecycle policy rules: select `tagged` (with `tagPrefixList` or `tagPatternList`) or `untagged` images, then `imageCountMoreThan`, `sinceImagePushed` or `sinceImagePulled`; images are expired or moved to archive. Rules are evaluated together and applied by priority (lower number first); expiry happens within 24 hours of meeting the criteria. Test with a lifecycle policy preview |
| Amazon S3 | Versioning plus lifecycle rules: transition to cheaper storage classes, expire objects and noncurrent versions; Object Lock for retention that cannot be shortened |
| AWS CodeArtifact | Package version status: `Published`, `Unfinished`, `Unlisted` (downloadable but not listed), `Archived` (not downloadable, can return to `Published` or `Unlisted`), `Disposed` (assets permanently deleted, irreversible); deleting a version allows republishing it |
| EC2 Image Builder | Lifecycle policies that deprecate, disable or delete AMIs or container images and their distributed copies, by count or age, run once a day |
| CodeBuild reports | Raw reports expire after 30 days unless exported to S3 |

```json
{
  "rules": [
    {
      "rulePriority": 1,
      "description": "Keep the 20 most recent release images",
      "selection": {
        "tagStatus": "tagged",
        "tagPatternList": ["release-*"],
        "countType": "imageCountMoreThan",
        "countNumber": 20
      },
      "action": { "type": "expire" }
    },
    {
      "rulePriority": 2,
      "description": "Remove untagged images after 7 days",
      "selection": {
        "tagStatus": "untagged",
        "countType": "sinceImagePushed",
        "countUnit": "days",
        "countNumber": 7
      },
      "action": { "type": "expire" }
    }
  ]
}
```

**Promotion** moves a version between environments without rebuilding it: add a `prod` tag to the image digest that passed staging (or replicate it to the production account's registry), promote a CodeArtifact version from a staging repository to a release repository with `copy-package-versions`, or copy the S3 object to the production bucket. Deploy by digest or exact version, never by a moving tag such as `latest`.

> **Exam trap.** An Image Builder lifecycle policy or an ECR lifecycle rule does not check whether a launch template, an Auto Scaling group or a running task definition still references the image. Keep enough versions for rollback (count rules) or exclude in-use images by tag before enabling deletion.

## Creating and configuring artifact repositories

**AWS CodeArtifact** organizes packages in a **domain** (one KMS key encrypts all its assets; each asset is stored once per domain however many repositories contain it; a domain policy controls which accounts can use it) that holds **repositories** (up to 1,000 per domain). A repository is polyglot: Maven, npm, PyPI, NuGet, Cargo, Ruby, Swift and generic packages. A repository can have **upstream repositories**, and at most **one external connection** to a public registry (`public:npmjs`, `public:pypi`, `public:maven-central`, `public:nuget-org` and others). The recommended layout puts each external connection on one repository that the other repositories use as upstream, so public packages are fetched and stored once.

```bash
aws codeartifact create-domain --domain example-corp --encryption-key arn:aws:kms:eu-west-1:111122223333:key/1a2b3c4d-5678-90ab-cdef-EXAMPLE22222
aws codeartifact create-repository --domain example-corp --repository npm-store
aws codeartifact associate-external-connection --domain example-corp --repository npm-store --external-connection public:npmjs
aws codeartifact create-repository --domain example-corp --repository team-apps --upstreams repositoryName=npm-store
aws codeartifact login --tool npm --domain example-corp --domain-owner 111122223333 --repository team-apps
```

Authentication uses a token: 12 hours by default, configurable from 15 minutes to 12 hours, or `--duration-seconds 0` to match the remaining session of an assumed role. Getting it needs both `codeartifact:GetAuthorizationToken` and `sts:GetServiceBearerToken`; the root user can't call it. Builds in private subnets use interface VPC endpoints for CodeArtifact plus S3 access for package assets.

**Amazon ECR** private repositories are configured per repository and per registry:

| Setting | Scope | Notes |
| --- | --- | --- |
| Tag mutability | Repository | `MUTABLE` (default), `IMMUTABLE`, `IMMUTABLE_WITH_EXCLUSION`; pushing an existing immutable tag returns `ImageTagAlreadyExistsException` |
| Encryption | Repository, at creation only | AES-256 by default, or KMS (`aws/ecr` or a customer managed key in the same Region); cannot be changed later |
| Repository policy | Repository | Grants cross-account pull (`ecr:BatchGetImage`, `ecr:GetDownloadUrlForLayer`, `ecr:BatchCheckLayerAvailability`); the puller also needs `ecr:GetAuthorizationToken` in its own policy |
| Scanning | Registry | Basic (AWS native, OS packages, on push or manual) or enhanced (Amazon Inspector, OS and language packages, on push and continuous) |
| Replication | Registry | Cross-Region and cross-account, filtered by repository prefix, up to 25 destinations; only images pushed after configuration (backfill for older ones); repository settings are not replicated; the destination registry policy allows `ecr:ReplicateImage` and `ecr:CreateRepository` |
| Pull through cache | Registry | Caches images from ECR Public, Quay, the Kubernetes registry, Docker Hub, GitHub, GitLab, Azure and Chainguard registries (credentials in a Secrets Manager secret named with the `ecr-pullthroughcache/` prefix) or another ECR registry; on a pull, ECR checks the upstream for a newer image if its last check is more than 24 hours old |
| Repository creation templates | Registry | Settings (policy, immutability, encryption, lifecycle) for repositories created by replication or pull through cache |

**Amazon S3** as an artifact store: versioning (required for an S3 pipeline source), default SSE-KMS encryption with a customer managed key when other accounts must read, Block Public Access, a bucket policy that limits access to pipeline and deployment roles, and lifecycle rules for old versions.

> **Exam trap.** Replication copies images, not repository policies, lifecycle policies or tag immutability; use repository creation templates or configure the destination repositories. And a pull through cache rule needs mutable tags to refresh a cached tag.

## Configuring build tools to generate artifacts

A CodeBuild project declares where its output goes: artifact type `S3`, `CODEPIPELINE` (the pipeline's artifact store) or `NO_ARTIFACTS`; packaging `ZIP` or `NONE`; optional build ID in the path; and **secondary artifacts** when one build produces several outputs. The buildspec `artifacts` section chooses the files:

```yaml
version: 0.2
phases:
  build:
    commands:
      - sam build
      - sam package --s3-bucket example-corp-artifacts-eu-west-1 --output-template-file packaged.yaml
      - mvn -q package
artifacts:
  files:
    - packaged.yaml
  secondary-artifacts:
    ServerlessTemplate:
      files:
        - packaged.yaml
    WebBundle:
      base-directory: web/target
      files:
        - '**/*'
      exclude-paths:
        - '**/*.map'
      name: web-$CODEBUILD_BUILD_NUMBER
      discard-paths: no
```

- `files` is always required, even with only secondary artifacts. Identifiers under `secondary-artifacts` must match the project's secondary artifact identifiers or, in CodePipeline, the action's output artifact names.
- `base-directory` sets the root of the output; `discard-paths: yes` flattens directories; `exclude-paths` removes files; `name` can use environment variables.
- Several sources are available in one build: the primary in `CODEBUILD_SRC_DIR`, each secondary source in `CODEBUILD_SRC_DIR_` followed by its identifier.
- `exported-variables` publish values such as the image tag to later pipeline actions.

**AWS Lambda** appears in two roles. As **CodeBuild compute**, it starts builds faster with no queue, for tools that don't need root (AWS CLI, SAM CLI, Node.js, Python, Java, .NET), within 15 minutes, without Docker, caching, VPC or privileged mode. As a **CodePipeline Lambda invoke action**, a function can generate or transform an artifact: the job data gives it the input and output artifact locations in the artifact bucket and temporary credentials to read and write them; it then reports `PutJobSuccessResult` or `PutJobFailureResult`.

> **Exam trap.** A build that must produce a container image cannot use Lambda compute (no Docker); a build that runs longer than 15 minutes cannot either. Choose EC2 compute, on demand or from a reserved capacity fleet.

## Automating EC2 instance and container image builds

**EC2 Image Builder** builds, tests and distributes AMIs and container images with no charge for the service itself (EC2, EBS, ECR, S3 and Amazon Inspector usage is billed):

| Resource | Role |
| --- | --- |
| Component | YAML document run by AWSTOE: **build** components customize the instance (build and validate phases); **test** components check an instance launched from the new image (test phase). AWS-managed components include hardening such as STIG |
| Image recipe / container recipe | Base image (an AMI, an AMI ID in a Parameter Store parameter, or for containers Docker Hub, ECR or Amazon-managed images) plus ordered components |
| Infrastructure configuration | Instance type, instance profile, subnet, security groups, logs to S3, SNS topic; option to keep a failed build instance for troubleshooting |
| Distribution configuration | Target Regions, AMI sharing with accounts, organizations and OUs, KMS keys, launch template updates; ECR repositories for container images |
| Image pipeline | Recipe + infrastructure + distribution, run manually or on a schedule (cron or rate expression in a time zone) |
| Workflows | Customize the build, test and distribution stages |
| Lifecycle policy | Deprecate, disable or delete old images and their distributed copies |

```yaml
name: install-nginx
description: Install nginx and verify that it serves requests
schemaVersion: 1.0
phases:
  - name: build
    steps:
      - name: InstallNginx
        action: ExecuteBash
        inputs:
          commands:
            - sudo dnf install -y nginx
            - sudo systemctl enable nginx
  - name: validate
    steps:
      - name: CheckBinary
        action: ExecuteBash
        inputs:
          commands:
            - nginx -v
  - name: test
    steps:
      - name: ServeRequest
        action: ExecuteBash
        inputs:
          commands:
            - sudo systemctl start nginx
            - curl -sf http://localhost/
```

Scheduling: the pipeline's start condition defaults to `EXPRESSION_MATCH_AND_DEPENDENCY_UPDATES_AVAILABLE`, which builds at the scheduled time only when a newer base image or component version matches the recipe's semantic version filters (a changed Parameter Store base image value counts); `EXPRESSION_MATCH_ONLY` builds every time. Enable **security scanning** in the pipeline to have Amazon Inspector (activated in the account) scan the image. The image is distributed only if all tests succeed.

A typical golden AMI flow: a monthly schedule or a new base AMI starts the Image Builder pipeline; tests and scanning gate it; distribution copies the AMI to every Region and shares it with the workload accounts' OU, and updates their launch templates to a new default version; an EventBridge rule on the image state change starts the next step, such as an Auto Scaling **instance refresh** or a pipeline that records the AMI ID in Parameter Store. Container images follow the same idea with a container recipe pushing to ECR, or with a CodeBuild `docker build` stage.

> **Exam trap.** Updating the launch template does not replace running instances: the Auto Scaling group needs an instance refresh or a new deployment. And a scheduled pipeline that "ran but produced no new image" is usually the default start condition with no dependency update; switch to `EXPRESSION_MATCH_ONLY` when every run must build.

## Key points

- Build once, deploy many: one immutable version (commit SHA, image digest), promoted through environments; deploy by digest, not `latest`.
- Integrity: AWS Signer code signing for Lambda (`Warn` or `Enforce`), ECR managed signing; immutability with ECR tag immutability, S3 versioning and Object Lock; CodeArtifact package origin controls stop dependency substitution.
- Lifecycle: ECR lifecycle rules (count, pushed, pulled; preview first; within 24 hours); S3 lifecycle; CodeArtifact statuses (`Unlisted`, `Archived`, `Disposed` is permanent); Image Builder lifecycle policies run daily and ignore downstream references.
- CodeArtifact: domain with one KMS key, up to 1,000 repositories, one external connection per repository, upstreams; 12-hour token by default (15 minutes to 12 hours), `GetAuthorizationToken` plus `sts:GetServiceBearerToken`.
- ECR: encryption fixed at creation; repository policy for cross-account pulls; replication of new images only, settings through creation templates; pull through cache with `ecr-pullthroughcache/` secrets; enhanced scanning with Amazon Inspector.
- CodeBuild artifacts: `files` always required, secondary artifacts matched by identifier, `base-directory`, `discard-paths`, `exclude-paths`; Lambda compute has no Docker and a 15-minute limit.
- Image Builder: components, recipes, infrastructure and distribution configurations, scheduled pipelines with dependency-update condition, Inspector scanning, launch template updates followed by an instance refresh.
