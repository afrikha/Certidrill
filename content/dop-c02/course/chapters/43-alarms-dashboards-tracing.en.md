Collected data becomes useful when an alarm watches the right metric with the right statistic, a dashboard shows the team what matters, and a trace explains where a slow request spent its time. This chapter covers anomaly detection alarms, the metrics and logs you must recognize for EC2, RDS, load balancers and serverless services, CloudWatch dashboards and Quick Sight visualizations, alarms on standard, custom and computed metrics, and tracing with AWS X-Ray across Lambda, API Gateway and containers.

## Anomaly detection alarms

A static threshold fails on metrics with a daily or weekly pattern: 2,000 requests per minute is normal at noon and alarming at 3 a.m. **CloudWatch anomaly detection** trains a model on up to two weeks of a metric (one model per metric and statistic), accounts for hourly, daily and weekly seasonality and trends, and draws an expected band.

| Fact | Detail |
| --- | --- |
| Band width | The anomaly detection threshold of `ANOMALY_DETECTION_BAND(m1, 2)`: a higher number gives a wider band and fewer alarms |
| Alarm direction | Above the band, below the band, or outside it (`LessThanLowerOrGreaterThanUpperThreshold`) |
| Inputs | A single metric or a metric math expression; source-account metrics from a monitoring account |
| Training | New models can take up to 3 hours to appear and up to two weeks to train fully; exclude deployment windows or incidents from training |
| Period | One minute or longer |
| Cost | Charged per alarm using a model; delete the alarm before the model, or the alarm recreates it |

```bash
aws cloudwatch put-anomaly-detector --single-metric-anomaly-detector \
  '{"Namespace":"AWS/ApplicationELB","MetricName":"RequestCount","Dimensions":[{"Name":"LoadBalancer","Value":"app/web/0123456789abcdef"}],"Stat":"Sum"}'

aws cloudwatch put-metric-alarm --alarm-name web-requests-anomaly \
  --comparison-operator LessThanLowerOrGreaterThanUpperThreshold \
  --evaluation-periods 3 --datapoints-to-alarm 2 --threshold-metric-id ad1 \
  --metrics '[{"Id":"m1","ReturnData":true,"MetricStat":{"Metric":{"Namespace":"AWS/ApplicationELB","MetricName":"RequestCount","Dimensions":[{"Name":"LoadBalancer","Value":"app/web/0123456789abcdef"}]},"Period":300,"Stat":"Sum"}},{"Id":"ad1","Expression":"ANOMALY_DETECTION_BAND(m1, 2)","ReturnData":true}]' \
  --alarm-actions arn:aws:sns:eu-west-1:111122223333:ops-alerts
```

Related features: **CloudWatch Logs anomaly detection** (Standard log groups) learns log patterns and flags unusual ones, and Logs Insights `pattern` groups similar events; **X-Ray Insights** flags unusual fault rates in traces.

> **Exam trap.** "Alert when traffic drops abnormally for the time of day, without maintaining thresholds" is an anomaly detection alarm with the lower bound (or both). A static alarm with a low threshold misses a drop at peak time and fires every night.

## Common CloudWatch metrics and logs to recognize

| Service (namespace) | Metric | What it tells you |
| --- | --- | --- |
| EC2 (`AWS/EC2`) | `CPUUtilization` | Compute saturation (5-minute basic, 1-minute detailed) |
| EC2 | `StatusCheckFailed_System` / `StatusCheckFailed_Instance` / `StatusCheckFailed_AttachedEBS` | AWS hardware or network (recover action) / guest OS issue (reboot action) / unreachable EBS volume |
| EC2 burstable | `CPUCreditBalance` | T instances running out of credits |
| RDS (`AWS/RDS`) | `DiskQueueDepth` | I/O requests waiting for the disk: the "queue length" of a storage bottleneck |
| RDS | `FreeStorageSpace`, `FreeableMemory`, `DatabaseConnections`, `ReplicaLag`, `ReadLatency` / `WriteLatency` | Storage exhaustion, memory pressure, connection limits, stale replicas, slow I/O |
| ALB (`AWS/ApplicationELB`) | `HTTPCode_ELB_5XX_Count` | Errors **generated by the load balancer**: 502 (bad target response), 503 (no registered targets), 504 (target timeout) |
| ALB | `HTTPCode_Target_5XX_Count` | Errors **returned by the targets** (application bugs) |
| ALB | `TargetResponseTime`, `UnHealthyHostCount`, `HealthyHostCount`, `RequestCountPerTarget`, `RejectedConnectionCount` | Latency, failing targets, scaling signal, capacity |
| Lambda (`AWS/Lambda`) | `Errors`, `Throttles`, `Duration`, `ConcurrentExecutions`, `IteratorAge` | Failures, concurrency limits, timeouts approaching, stream consumers falling behind |
| SQS (`AWS/SQS`) | `ApproximateNumberOfMessagesVisible`, `ApproximateAgeOfOldestMessage` | Backlog; consumers too slow or failing |
| API Gateway (`AWS/ApiGateway`) | `5XXError`, `4XXError`, `Latency`, `IntegrationLatency` | Server errors, client errors, total versus backend time |
| DynamoDB (`AWS/DynamoDB`) | `ThrottledRequests`, `ReadThrottleEvents`, `WriteThrottleEvents`, `SystemErrors` | Capacity or hot partitions |
| ECS (`AWS/ECS`) | `CPUUtilization`, `MemoryUtilization` by cluster and service | Service saturation |

Logs that answer common questions: Lambda `REPORT` lines (duration, billed duration, max memory used), ALB access logs (`elb_status_code` versus `target_status_code`, `target_processing_time`), VPC Flow Logs (`REJECT` records for blocked traffic), CloudTrail events (`errorCode` such as `AccessDenied`, console sign-in failures).

> **Exam trap.** Users get 502 errors and `HTTPCode_ELB_5XX_Count` rises while `HTTPCode_Target_5XX_Count` stays flat: the load balancer can't get a valid response from the targets (crash, closed connection, health check path), not an application error page.

## CloudWatch dashboards and Quick Sight visualizations

**CloudWatch dashboards** are global (one dashboard can show several Regions) and, with cross-account observability or the cross-account cross-Region console, several accounts.

| Widget or feature | Use |
| --- | --- |
| Line, stacked area, number, gauge, bar, pie | Metrics and metric math, including Metrics Insights queries |
| Alarm status | All alarms of a service or team on one widget |
| Logs Insights table or graph | A saved query result, refreshed with the dashboard |
| Text | Runbook links, owners |
| Custom widget | A Lambda function that returns HTML or data (for example, a deployment status from another API) |
| Variables | One dashboard switches between instances, Regions or environments |
| Automatic dashboards | Per-service dashboards that CloudWatch builds for you |

Dashboards are JSON documents: deploy them with CloudFormation (`AWS::CloudWatch::Dashboard`) or `put-dashboard`, so every environment gets the same view. Share them with up to five email addresses, a public link, or an SSO provider; a shared dashboard lets viewers read the account's metrics, not only its widgets.

```json
{
  "widgets": [{
    "type": "metric", "x": 0, "y": 0, "width": 12, "height": 6,
    "properties": {
      "title": "ALB 5xx by source",
      "region": "eu-west-1", "stat": "Sum", "period": 60,
      "metrics": [
        ["AWS/ApplicationELB", "HTTPCode_ELB_5XX_Count", "LoadBalancer", "app/web/0123456789abcdef"],
        [".", "HTTPCode_Target_5XX_Count", ".", "."]
      ]
    }
  }]
}
```

**Amazon Quick Sight** (now AWS Quick Sight, a feature of AWS Quick) is for business-style analysis of large log datasets, not operational alarms: point it at **Athena** tables over CloudTrail, ALB access logs, VPC Flow Logs or metric stream data in S3, import into SPICE on a refresh schedule, and build interactive dashboards for auditors or managers who have no CloudWatch access. **Amazon Managed Grafana** is the choice for Prometheus and multi-source operational dashboards.

| Requirement | Answer |
| --- | --- |
| On-call view of health across Regions and accounts | CloudWatch dashboard with alarm status and cross-account metrics |
| Monthly trends of API calls by user from a year of CloudTrail logs, for managers | Athena over the S3 trail plus Quick Sight |
| Prometheus metrics from EKS with existing Grafana dashboards | Managed Service for Prometheus plus Managed Grafana |

## Associating CloudWatch alarms with standard and custom metrics

An alarm names **exactly** one metric (namespace, name, full dimension set, optionally unit) or a metric math expression, a statistic (`--statistic` or `--extended-statistic p99`), a period, evaluation periods and datapoints to alarm (M out of N), a threshold and the missing data treatment.

| Metric | Alarm detail |
| --- | --- |
| Standard AWS metric | Dimensions as the service publishes them (`InstanceId`, `LoadBalancer` plus `TargetGroup`, `DBInstanceIdentifier`) |
| EC2 basic monitoring | Period of at least 300 seconds; detailed monitoring for 60 seconds |
| Custom metric (agent, EMF, `PutMetricData`) | Same namespace and dimension set as published (agent metrics carry the dimensions you appended); a wrong `--unit` leaves the alarm in `INSUFFICIENT_DATA` |
| High-resolution custom metric | Alarm periods of 10 or 30 seconds (charged more) or multiples of 60 |
| Ratio or sum of metrics | Metric math alarm (error rate = errors / requests), one alarm instead of several |
| Many resources at once | Alarm on a **Metrics Insights** query (for example the highest CPU across every instance of a fleet, including instances launched later) |

```bash
aws cloudwatch put-metric-alarm --alarm-name checkout-error-rate \
  --evaluation-periods 5 --datapoints-to-alarm 3 \
  --comparison-operator GreaterThanThreshold --threshold 2 \
  --treat-missing-data notBreaching \
  --metrics '[{"Id":"e","Expression":"100*errors/requests","Label":"ErrorRate","ReturnData":true},
    {"Id":"errors","MetricStat":{"Metric":{"Namespace":"AWS/ApplicationELB","MetricName":"HTTPCode_Target_5XX_Count","Dimensions":[{"Name":"LoadBalancer","Value":"app/web/0123456789abcdef"}]},"Period":60,"Stat":"Sum"},"ReturnData":false},
    {"Id":"requests","MetricStat":{"Metric":{"Namespace":"AWS/ApplicationELB","MetricName":"RequestCount","Dimensions":[{"Name":"LoadBalancer","Value":"app/web/0123456789abcdef"}]},"Period":60,"Stat":"Sum"},"ReturnData":false}]' \
  --alarm-actions arn:aws:sns:eu-west-1:111122223333:oncall
```

Missing data choices: `missing` (default, the alarm looks further back), `notBreaching` (sparse error counts), `breaching` (a heartbeat metric whose absence is the failure), `ignore` (keep the current state). Percentile alarms on few samples can ignore or evaluate low-sample periods.

> **Exam trap.** A metric filter that counts errors publishes nothing in minutes without log events, so a `missing` alarm flaps or sits in `INSUFFICIENT_DATA`. Set the filter's default value to 0 or treat missing data as `notBreaching`. For "alert if the job stops reporting", treat missing data as `breaching`.

## Configuring AWS X-Ray for Lambda, API Gateway and containers

X-Ray assembles **traces** from **segments** (one per service) and **subsegments** (downstream calls), shown on the **trace map**. **Annotations** are indexed key/value pairs usable in filter expressions and groups; **metadata** is not indexed. **Sampling rules** (priority, reservoir per second, fixed rate, matched on service name and type, host, method, URL path) control cost; the default records the first request each second and 5 % of the rest. The X-Ray SDKs and daemon are in **maintenance mode** since February 25, 2026 (security fixes only): instrument new code with **AWS Distro for OpenTelemetry (ADOT)** or CloudWatch **Application Signals**, which still send traces to X-Ray.

| Service | How to turn on tracing | Permissions and notes |
| --- | --- | --- |
| Lambda | `TracingConfig: Mode: Active` (SAM: `Tracing: Active`; CLI `--tracing-config Mode=Active`) | Execution role with `AWSXRayDaemonWriteAccess`; sampling for functions isn't configurable (1 request per second plus 5 %); upstream sampling decisions are honored; add the ADOT Lambda layer for downstream call detail |
| API Gateway REST API | Enable X-Ray tracing on the **stage** | Sampling rules with service type `AWS::APIGateway::Stage` and service name `api-name/stage`; **HTTP APIs don't support X-Ray tracing** |
| ECS on Fargate or EC2 | Sidecar container in the task: ADOT collector or CloudWatch agent receiving OTLP (or X-Ray segments) | **Task role** with `AWSXRayDaemonWriteAccess`; the application sends to the sidecar on localhost |
| EKS | ADOT add-on or the CloudWatch Observability add-on (Application Signals) | IAM through EKS Pod Identity or IAM roles for service accounts |
| EC2 | CloudWatch agent with trace collection (or an ADOT collector) | Instance profile with `AWSXRayDaemonWriteAccess` |
| Elastic Beanstalk | `XRayEnabled` option of the environment | Runs the X-Ray daemon (maintenance mode) on the instances; instance profile permissions |
| Step Functions | Enable tracing on the state machine | Execution role permissions |
| ALB, SNS, SQS, EventBridge | Pass the trace header (`X-Amzn-Trace-Id`) so traces continue | No segment of their own for ALB |

```yaml
Resources:
  OrdersFunction:
    Type: AWS::Serverless::Function
    Properties:
      Handler: app.handler
      Runtime: python3.12
      CodeUri: src/
      Tracing: Active
  OrdersApi:
    Type: AWS::Serverless::Api
    Properties:
      StageName: prod
      TracingEnabled: true
```

Filter expressions find the traces that matter:

```text
service("checkout") { fault = true } AND annotation.tier = "gold"
responsetime > 2 AND http.url CONTAINS "/payment"
```

> **Exam trap.** "Traces show the API Gateway stage and the Lambda service node but no DynamoDB calls" means the function's code isn't instrumented: active tracing records only the invocation. Add ADOT (or Application Signals) instrumentation to capture downstream calls.

> **Exam tip.** "Trace requests across an ECS service with the least change to the long-term toolchain" points to an ADOT or CloudWatch agent sidecar with OpenTelemetry, not the X-Ray daemon image and SDK, which are in maintenance mode.

## Key points

- Anomaly detection: model per metric and statistic, up to two weeks of training, band width set in `ANOMALY_DETECTION_BAND(m1, n)`, alarm above, below or outside the band.
- Recognize the metrics: `DiskQueueDepth` for RDS I/O queues, `HTTPCode_ELB_5XX_Count` versus `HTTPCode_Target_5XX_Count`, `StatusCheckFailed_System` for recover, `ApproximateAgeOfOldestMessage`, `IteratorAge`, `Throttles`.
- CloudWatch dashboards are global JSON documents with cross-account widgets, variables and Logs Insights widgets; Quick Sight on Athena for long-range analysis of log data in S3.
- Alarms must match namespace, dimensions and unit; high-resolution alarms at 10 or 30 seconds; metric math and Metrics Insights alarms; choose missing data treatment deliberately.
- X-Ray: active tracing on Lambda, stage tracing on REST APIs (not HTTP APIs), sidecars on ECS, add-ons on EKS; `AWSXRayDaemonWriteAccess`; instrument with ADOT or Application Signals because the X-Ray SDKs and daemon are in maintenance mode.
