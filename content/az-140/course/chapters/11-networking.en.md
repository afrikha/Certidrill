Azure Virtual Desktop connections never reach the session hosts through an inbound port: both the client and the session host connect out to the service, and RDP then tries to move to a faster UDP path. Exam questions describe a network and ask which transport users get, what to open or configure, or why a connection is slow.

<!-- section: connectivity-model | objectives: 1.1.1, 1.1.2 -->
## How a connection is established

1. The client subscribes to a workspace; Microsoft Entra ID authenticates the user and returns a token.
2. The feed service validates the token and returns the desktops and apps as digitally signed `.rdp` configuration.
3. When the user connects, the client opens a TLS connection to a **gateway** through Azure Front Door. Gateways are grouped by latency in 10 ms bands; the one with the lowest latency, then the fewest connections, wins.
4. The gateway asks the **broker** to orchestrate. The broker uses the persistent channel that the session host's Remote Desktop Agent Loader opened at startup.
5. The session host opens its own TLS connection to the **same gateway instance**, which relays the traffic: this is the **reverse connect** transport, over TCP 443.
6. RDP runs a nested TLS connection between client and session host, then tries RDP Shortpath (UDP). If UDP works, the TCP transport is dropped; otherwise TCP remains.

| Fact | Value |
| --- | --- |
| Inbound ports needed on session hosts for reverse connect | None |
| Minimum TLS version to the service | TLS 1.2 (TLS 1.3 when the OS supports it) |
| RDP certificate | Self-generated by the OS; certificates issued by a certificate authority aren't supported |
| Latency target from the client network to the host pool region | Round-trip time less than 150 ms |

> **Exam trap.** Opening inbound TCP 3389 to session hosts is never required for users. Microsoft recommends not opening it, and not giving session hosts public IP addresses; use just-in-time VM access if you must troubleshoot over RDP.

<!-- section: capacity-speed | objectives: 1.1.1 -->
## Network capacity and speed

RDP has no fixed bandwidth: it measures available bandwidth and round-trip time continuously and adapts encoding, frame rate and compression. Only changed screen regions are sent; an idle or minimized session sends almost nothing. Bandwidth grows with graphics richness, frame rate and resolution.

Microsoft's reference figures, one 1920 × 1080 monitor:

| Activity | Default mode | H.264/AVC 444 mode |
| --- | --- | --- |
| Idle | 0.3 Kbps | 0.3 Kbps |
| Microsoft Word | 100–150 Kbps | 200–300 Kbps |
| Microsoft Excel | 150–200 Kbps | 400–500 Kbps |
| Microsoft PowerPoint | 4–4.5 Mbps | 1.6–1.8 Mbps |
| Web browsing | 6–6.5 Mbps | 0.9–1 Mbps |
| Video playback, half screen, 30 FPS | 8.5–9.5 Mbps | 2.5–2.8 Mbps |

Assessing a site:

| Requirement | Answer |
| --- | --- |
| Estimate the bandwidth of a branch office | Monitor real sessions with performance counters or network equipment (the best method); otherwise map user work patterns to the reference table and multiply by concurrent users |
| Users far from the region complain about lag | Measure round-trip time; place session hosts in the region closest to users (target less than 150 ms) |
| Limit RDP bandwidth on a metered or constrained link | Policy-based QoS with an outbound throttle rate on `svchost.exe`, UDP source port 3390. Requires RDP Shortpath for managed networks: throttling isn't supported on reverse connect |

```powershell
New-NetQosPolicy -Name "RDP Shortpath for managed networks" -AppPathNameMatchCondition "svchost.exe" -IPProtocolMatchCondition UDP -IPSrcPortStartMatchCondition 3390 -IPSrcPortEndMatchCondition 3390 -ThrottleRateActionBitsPerSecond 10mb -NetworkProfile All
```

<!-- section: session-host-network | objectives: 1.1.2 -->
## Network configuration for session hosts

Requirements:

- A virtual network and subnet **in the same region as the session hosts**, created before the host pool if you deploy session hosts in the same wizard.
- With AD DS or Microsoft Entra Domain Services, connectivity to the domain controllers and DNS servers so hosts can join the domain: set the virtual network's DNS servers to them (custom DNS servers forward to Azure DNS for other names).
- Outbound access to the required endpoints, and to the Microsoft 365 endpoints if users run Microsoft 365 Apps. Microsoft doesn't support deployments where they are blocked.

Main required endpoints of session hosts (Azure cloud):

| Address | Port | Purpose | Service tag |
| --- | --- | --- | --- |
| `*.wvd.microsoft.com` | TCP 443 | Service traffic and TCP-based RDP | `WindowsVirtualDesktop` |
| `login.microsoftonline.com` | TCP 443 | Authentication | `AzureActiveDirectory` |
| `51.5.0.0/16` | UDP 3478 | Relayed RDP connectivity (TURN) | `WindowsVirtualDesktop` |
| `*.prod.warm.ingest.monitor.core.windows.net`, `gcs.prod.monitoring.core.windows.net` | TCP 443 | Agent traffic | `AzureMonitor` |
| `azkms.core.windows.net` | TCP 1688 | Windows activation | `Internet` |
| `mrsglobalsteus2prod.blob.core.windows.net` | TCP 443 | Agent and side-by-side stack updates | `Storage` |
| `169.254.169.254` and `168.63.129.16` | TCP 80, and more for 168.63.129.16 | Instance Metadata Service and platform connectivity: never intercept, proxy or redirect | None |

Design rules:

| Requirement | Answer |
| --- | --- |
| Filter session host egress centrally | Hub-and-spoke: session hosts in a spoke, route `0.0.0.0/0` to Azure Firewall in the hub, allow the `WindowsVirtualDesktop` service tag and the required FQDNs |
| New virtual network, no NVA, hosts need internet access | Explicit outbound method: a NAT gateway on the subnet. New virtual networks default to private subnets, and Windows activation and updates need explicit egress |
| Check that a session host reaches every required endpoint | Azure Virtual Desktop Agent URL Tool, `WVDAgentUrlTool.exe`, in the RDAgent folder of the session host. It doesn't test wildcard entries |
| An existing web proxy | Bypass it for Azure Virtual Desktop traffic (PAC file, bypass list, service tags in Azure Firewall); no SSL inspection, no proxy that requires authentication |

> **Exam trap.** A proxy that is the only path out forces RDP over TCP instead of UDP. TLS inspection replaces the service certificates and can stop the agent from working: Microsoft asks you to disable it before you open a support case.

<!-- section: rdp-shortpath | objectives: 1.1.3 -->
## RDP Shortpath

RDP Shortpath adds a UDP transport between client and session host, using the Universal Rate Control Protocol (URCP) on top of UDP. It is established after authentication over reverse connect, and it keeps the same security: TLS over reliable UDP.

| Option | Network | How | Ports |
| --- | --- | --- | --- |
| Managed networks | ExpressRoute private peering, site-to-site or point-to-site VPN | Direct UDP to a listener on the session host | Inbound UDP 3390 (default, configurable) on each session host |
| Managed networks with ICE/STUN | Private network | Direct UDP after NAT traversal | No inbound port |
| Public networks with ICE/STUN | Internet | Direct UDP; the session host learns its public IP:port from a STUN server | UDP 3478 to STUN; UDP 49152–65535 by default for the data flow |
| Public networks via TURN | Internet | UDP relayed by a TURN server (Azure public cloud) | UDP 3478 to `51.5.0.0/16` |

Rules to know:

- In the host pool, each option is on the **Networking > RDP Shortpath** page and is set to **Default**, which means enabled. UDP is enabled in Windows by default on hosts and clients.
- If the host pool setting and the session host setting conflict, the **more restrictive** wins.
- The managed listener needs the policy **Enable RDP Shortpath for managed networks** (Administrative templates > Windows Components > Remote Desktop Services > Remote Desktop Session Host > Azure Virtual Desktop), the inbound port allowed in Windows Firewall and NSGs, and a restart.
- When managed and public paths are both possible, the first connection established wins; the managed path usually does.
- **Symmetric NAT** (Azure Firewall and Azure NAT Gateway are examples) prevents a direct STUN path: the connection uses TURN. Microsoft strongly recommends keeping TURN enabled.
- To shrink the client UDP port range, enable **Use port range for RDP Shortpath for unmanaged networks** (default base port 38300, pool of 1000 ports, inside 1024–49151).
- If UDP is blocked on every path, the session stays on TCP reverse connect.

Verify the transport in **Connection Information** on the connection bar: **UDP (Private Network)** for the managed listener, **UDP** for STUN, **UDP (Relay)** for TURN. `avdnettest.exe` tests STUN connectivity and the NAT type; a cone-shaped NAT means public Shortpath is very likely to work.

> **Exam trap.** The policy that enables the 3390 listener is needed only for the managed listener option. Public Shortpath (STUN, TURN) needs no inbound port at all, only outbound UDP from session hosts.

<!-- section: rdp-multipath | objectives: 1.1.3 -->
## RDP Multipath

RDP Multipath monitors several network paths at once and uses the most reliable one, with backup paths on standby. ICE discovers several UDP paths (STUN and TURN), and Azure Virtual Desktop can also keep TCP reverse connect paths as standby. If the active path degrades, the session switches to the next best one; if all paths are lost, it reconnects when the network returns.

| Item | Value |
| --- | --- |
| Availability | Generally available, Azure public cloud and Azure Government |
| Configuration | None beyond RDP Shortpath: it works automatically once prerequisites are met |
| Windows App for Windows | 2.0.559.0 or later for multiple UDP paths; 2.0.1069.0 or later for redundant TCP paths |
| Other platforms | Windows App for macOS Beta for multiple UDP paths; others not supported |
| Endpoints | TCP 443 to `*.wvd.microsoft.com`, UDP 3478 and UDP 1024–65535 to `51.5.0.0/16` |

<!-- section: qos | objectives: 1.1.3 -->
## Quality of service

QoS prioritizes RDP traffic on congested managed links. It applies only to **RDP Shortpath for managed networks**: QoS policies aren't supported for reverse connect. It must be applied on every link between client and session host, so a user at home is prioritized only inside your managed network.

Recommended marking: **DSCP 46, Expedited Forwarding**, on session hosts. With Group Policy: **Computer Configuration > Windows Settings > Policy-based QoS > Create new policy**, DSCP 46, executable `svchost.exe`, any source and destination IP address, UDP, source port 3390, then `gpupdate /force`.

```powershell
New-NetQosPolicy -Name "RDP Shortpath for managed networks" -AppPathNameMatchCondition "svchost.exe" -IPProtocolMatchCondition UDP -IPSrcPortStartMatchCondition 3390 -IPSrcPortEndMatchCondition 3390 -DSCPAction 46 -NetworkProfile All
```

> **Exam tip.** Same policy, two goals: `-DSCPAction 46` prioritizes, `-ThrottleRateActionBitsPerSecond` limits. Both match UDP source port 3390, so both need RDP Shortpath for managed networks.

<!-- section: private-link | objectives: 1.1.4 -->
## Azure Private Link

Private Link lets clients and session hosts reach Azure Virtual Desktop through private endpoints over the Microsoft network; users reach the virtual network over VPN or ExpressRoute.

| Purpose | Resource | Sub-resource | How many |
| --- | --- | --- | --- |
| Connections to the host pool | Host pool | `connection` | One per host pool |
| Feed download | Workspace | `feed` | One per workspace |
| Initial feed discovery | Workspace | `global` | One for all your Azure Virtual Desktop deployments |

| Requirement | Endpoints needed |
| --- | --- |
| Everything private, including discovery | `connection` + `feed` + `global` |
| Feed and sessions private, discovery public | `connection` + `feed` |
| Only remote sessions private | `connection` |

Implementation order:

1. **Re-register** the `Microsoft.DesktopVirtualization` resource provider on each subscription.
2. Create the private endpoints (resource > **Networking** > **Private endpoint connections**), in a subnet in the same region as the virtual network and session hosts, and integrate them with private DNS zones: `privatelink.wvd.microsoft.com` for `connection` and `feed`, `privatelink-global.wvd.microsoft.com` for `global`.
3. Set **public access**. Host pool: **Enable public access from all networks**, **Enable public access for end users, use private access for session hosts**, or **Disable public access and use private access**. Workspace: enable from all networks, or disable and use private access.
4. Optionally block public routes with NSGs or Azure Firewall using the `WindowsVirtualDesktop` service tag, without blocking the required endpoints.
5. Restart the **RDAgentBootLoader** service on each session host (or the hosts), then check that endpoint connections are **Approved** and session hosts **Available**.

Rules to know:

- Put the `global` sub-resource on a **dedicated placeholder workspace** with no application groups. Its access settings are ignored, and deleting it stops feed discovery for every deployment.
- Don't restrict ports to the `connection` endpoint: session traffic uses TCP 1–65535 through one private IP address.
- UDP over Private Link is blocked by default. For RDP Shortpath for managed networks over Private Link, select **Allow Direct UDP network path over Private Link** and disable the public STUN and TURN options; the portal refuses to save otherwise.

> **Exam trap.** With **Disable public access and use private access** on the host pool, a connection works only when **both** the client and the session host use private routes. With the "end users public, session hosts private" option, the client route doesn't matter.

<!-- section: monitor-troubleshoot | objectives: 1.1.5 -->
## Monitor and troubleshoot connectivity

| Symptom or need | Tool |
| --- | --- |
| Which transport does this session use, what is its round-trip time? | **Connection Information** in the client |
| Session hosts show as unavailable after a firewall change | `WVDAgentUrlTool.exe` on the host; then the Azure Firewall or NSG logs |
| Will public Shortpath work from this network? | `avdnettest.exe` (STUN reachability and NAT type) |
| Round-trip time by gateway region, slowest users | Azure Virtual Desktop Insights, **Connection Performance** (ideal RTT below 100 ms, low quality above 200 ms) |
| Disconnections over time, by transport, client or gateway region | Azure Virtual Desktop Insights, **Connection Reliability** |
| Route or NSG blocking a flow from a session host | Network Watcher: IP flow verify, next hop, connection troubleshoot |

Connection network data is sent to Log Analytics every two minutes during an active session, in the `WVDConnectionNetworkData` table (`EstRoundTripTimeInMs`, `EstAvailableBandwidthKBps`, `CorrelationId`). `WVDConnections` holds one record per connection state with `TransportType`, `GatewayRegion`, `IsClientPrivateLink` and `IsSessionHostPrivateLink`.

```kusto
WVDConnectionNetworkData
| where TimeGenerated > ago(24h)
| join kind=inner (WVDConnections | distinct CorrelationId, UserName, TransportType) on CorrelationId
| summarize AvgRttMs = avg(EstRoundTripTimeInMs), AvgBandwidthKBps = avg(EstAvailableBandwidthKBps) by UserName, TransportType
| order by AvgRttMs desc
```

Above 200 ms of round-trip time, users may see input delay and disconnections. Reduce it with session hosts closer to users and fewer hops (proxies, inspection), and check the host's CPU and memory: an overloaded host also slows responses.

<!-- section: key-points -->
## Key points

- Reverse connect: client and session host connect out on TCP 443; no inbound port, no public IP on session hosts.
- Target round-trip time less than 150 ms to the host pool region; measure real sessions for bandwidth.
- Shortpath managed: listener on UDP 3390 (or STUN) over ExpressRoute or VPN. Shortpath public: STUN, then TURN on UDP 3478 to `51.5.0.0/16`. Symmetric NAT means TURN.
- RDP Multipath needs no setting of its own, only RDP Shortpath and a recent Windows App.
- QoS (DSCP 46) and throttling work only with RDP Shortpath for managed networks.
- Private Link: `connection` per host pool, `feed` per workspace, one `global` on a placeholder workspace; re-register the provider; two private DNS zones.
