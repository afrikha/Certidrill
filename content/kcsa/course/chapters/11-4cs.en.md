The 4Cs model splits cloud native security into four nested layers: Cloud, Cluster, Container and Code. The exam uses it to check that you can place a control in the right layer and that you understand why a weak outer layer cannot be compensated by a strong inner one. Kubernetes documentation now presents the same ideas by lifecycle phase, so you need both views.

## The four layers

The model comes from the Kubernetes documentation page "Overview of Cloud Native Security", still readable in the archived documentation of older releases (for example [v1.28](https://v1-28.docs.kubernetes.io/docs/concepts/security/overview/)). It draws the four layers as concentric boxes, **Cloud** outermost and **Code** innermost:

| Layer | What it covers | Typically owned by |
| --- | --- | --- |
| **Cloud** | The infrastructure the cluster runs on: a cloud provider, a co-located datacenter or a corporate datacenter, with its network, identities and storage | Cloud provider and infrastructure team |
| **Cluster** | The Kubernetes components (API server, etcd, kubelet...) and the configuration of the workloads running in the cluster | Platform or cluster operators |
| **Container** | The container images, the container runtime and the isolation of each container from the node | Platform team and image builders |
| **Code** | The application itself, its dependencies and the way it communicates | Developers |

Each layer **builds on the next outermost layer**. The cloud is the trusted computing base of the cluster: if an attacker controls the hypervisor, the node operating system or the cloud account, every control inside the cluster can be bypassed. The documentation put it bluntly: you cannot make up for poor security in the base layers by securing the code.

The reverse also matters: a perfectly hardened cloud and cluster still run vulnerable code. An injection flaw in the application gives an attacker a foothold in a container, and from there the inner layers decide how far they get.

> **Exam trap.** The order is Cloud, Cluster, Container, Code, from the outside in. A question asking which layer "everything else depends on" or which is "the trusted computing base" expects Cloud, not Code.

## Controls in each layer

Questions often name a control and ask which layer it belongs to. The guidance attached to each layer gives the answer:

| Layer | Controls |
| --- | --- |
| **Cloud** (infrastructure) | API server not exposed publicly, access restricted to known networks; nodes accept traffic only from the control plane and for NodePort and LoadBalancer Services; least-privilege cloud permissions for the cluster; etcd reachable only from the control plane; encryption of disks at rest; the provider's own security recommendations |
| **Cluster** | RBAC authorization, authentication, Secrets management and encryption at rest in etcd, Pod Security Standards, resource requests, limits and quotas, NetworkPolicy, TLS for Ingress, audit logging |
| **Container** | Vulnerability scanning of images at build time, image signing to keep a chain of trust, users with the least operating system privilege (no root), runtime classes that provide stronger isolation |
| **Code** | TLS for traffic in transit (mutual TLS between services), exposing only the ports the service needs, scanning third-party dependencies, static code analysis, dynamic probing of the running service (SQL injection, cross-site request forgery, cross-site scripting), for example with OWASP ZAP |

Some controls sit on a boundary, and the exam picks the layer named by the guidance:

- **Encryption at rest of etcd** appears both under Cloud (the storage of the infrastructure) and under Cluster (encrypting Secrets through the API server). If the question says "EncryptionConfiguration" or "Secrets", answer Cluster.
- **Running as a non-root user** is a Container control when it is about the image's default user, and a Cluster control when it is enforced by Pod Security Admission.
- **TLS between microservices** is a Code control in the 4Cs guidance even if a service mesh delivers it at the platform level.

> **Exam tip.** Ask "who configures this?". A cloud console or the network around the cluster points to Cloud; a Kubernetes object or API server flag points to Cluster; a Dockerfile, a registry or a runtime points to Container; the application source points to Code.

## Defense in depth and the lifecycle phases

The 4Cs are an illustration of **defense in depth**: several independent layers of controls, so that the failure of one control doesn't expose the whole system. A container escape is stopped by a hardened node; a stolen ServiceAccount token is limited by RBAC; a compromised Pod is contained by NetworkPolicy; an intrusion that gets through is seen in the audit logs and runtime alerts.

The current Kubernetes page, [Cloud Native Security and Kubernetes](https://kubernetes.io/docs/concepts/security/cloud-native-security/), no longer draws the 4Cs. It follows the [CNCF Cloud Native Security Whitepaper](https://tag-security.cncf.io/community/resources/security-whitepaper/v2/cloud-native-security-whitepaper/) (version 2, 2022) and organizes controls by **lifecycle phase**:

| Phase | Goal | Examples of controls |
| --- | --- | --- |
| **Develop** | Integrity of the development environment, secure design and code | Zero trust architecture, security-aware code review, threat modeling with trust boundaries, scanning of infrastructure as code and manifests, fuzzing |
| **Distribute** | Secure supply chain for images and cluster components | Image and artifact scanning, signing and signature validation, private registry that only authorized clients can pull from, up-to-date dependencies |
| **Deploy** | Restrict what can be deployed, who can deploy it and where | Pre-deployment checks of image signatures and policies, limits on who can deploy, namespaces to isolate workloads |
| **Runtime** | Protect running workloads: access, compute, storage, networking, observability | Authentication and authorization of the API, TLS everywhere, Pod Security Standards enforced, immutable node OS, seccomp and AppArmor, sandboxed runtimes, encryption at rest, NetworkPolicy and service mesh, tamper-proof logs |

The two views are complementary: the 4Cs say **where** a control lives, the lifecycle phases say **when** it applies. Image scanning, for example, is a Container control applied in the Distribute phase, and again at Runtime because new vulnerabilities are published after the image was built.

| 4Cs layer | Most of its controls apply in |
| --- | --- |
| Code | Develop |
| Container | Distribute (build, scan, sign), Runtime (isolation) |
| Cluster | Deploy (admission, RBAC), Runtime (audit, NetworkPolicy) |
| Cloud | Runtime (infrastructure access, node hardening, encrypted storage) |

> **Exam trap.** The KCSA curriculum still names "The 4Cs of Cloud Native Security", but if a question asks how kubernetes.io or the CNCF whitepaper structures security today, the answer is the lifecycle phases Develop, Distribute, Deploy and Runtime.

## Key points

- 4Cs, outside in: Cloud, Cluster, Container, Code. Each layer depends on the security of the layers around it; the cloud is the trusted computing base.
- Cloud: network access to the API server, nodes and etcd, least-privilege cloud permissions. Cluster: RBAC, Pod Security Standards, NetworkPolicy, Secrets, audit. Container: scanning, signing, non-root users, stronger runtimes. Code: TLS, minimal ports, dependency scanning, SAST and DAST.
- The model applies defense in depth: independent layers, so one failed control doesn't expose everything.
- Kubernetes documentation and the CNCF Cloud Native Security Whitepaper now organize security by lifecycle phase: Develop, Distribute, Deploy, Runtime.
