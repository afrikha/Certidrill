Evaluation measures whether a generative AI application or agent gives answers that are correct, grounded, relevant, well written and safe, before release and after every change. In Microsoft Foundry you prepare a test dataset, map its fields to evaluators, run built-in quality and safety evaluators (plus your own), and automate the run in a pipeline that blocks a regression. Exam questions ask which evaluator measures a given problem, which fields it needs, how to read its score, and how to wire the evaluation into a workflow.

## Test datasets and data mapping

An evaluation dataset is a JSONL or CSV file (or inline items) whose fields feed the evaluators. Three shapes exist:

| Dataset | Contains | Use |
| --- | --- | --- |
| Query and response | `query`, `response`, and optionally `context`, `ground_truth` | Evaluate outputs already produced (logs, a previous run) |
| Query only, with a target | `query` (and `ground_truth` if needed); the model or agent generates the response during the run | Evaluate a model deployment or an agent version directly |
| Messages | A `messages` array in OpenAI message format, possibly with tool calls | Multi-turn conversations; required for conversation-level evaluation. For a model or agent target, the array ends with a `user` message |

```json
{"query": "What is the return window?", "context": "Returns are accepted within 30 days of delivery.", "response": "You can return items within 30 days of delivery.", "ground_truth": "30 days after delivery."}
```

Fields required by common evaluators:

| Evaluator | Required fields |
| --- | --- |
| Coherence | `query`, `response` (or `messages`) |
| Fluency | `response` (or `messages`) |
| Groundedness | `response` and `context` (`context` is optional but recommended, and needed when `query` and `response` are strings; an agent response with tool calls can supply it); `query` optional but improves accuracy |
| Relevance | `query`, `response` |
| Retrieval | `query`, `context` |
| Response completeness | `response`, `ground_truth` |
| F1, BLEU, ROUGE, GLEU, METEOR, similarity | `response`, `ground_truth` |
| Content safety (violence, sexual, self-harm, hate and unfairness) | `query`, `response` (or `messages`) |

**Data mapping** connects dataset fields to evaluator inputs. In cloud evaluations (Foundry SDK and portal):

| Expression | Refers to |
| --- | --- |
| `{{item.query}}` | The `query` field of the dataset row; if your file uses `question`, map `{{item.question}}` |
| `{{sample.output_text}}` | The plain-text response generated by the model or agent target during the run |
| `{{sample.output_items}}` | The structured output of an agent, including tool calls (needed by agent evaluators such as task adherence) |

Sample fields are available only when the data source configuration sets `include_sample_schema=True`. The local Azure AI Evaluation SDK uses another syntax in `column_mapping`: `${data.query}` for dataset fields and `${outputs.response}` for the outputs of a target callable.

Building the dataset:

| Source | How | Notes |
| --- | --- | --- |
| Curated file | `project_client.datasets.upload_file(name=..., version=..., file_path=...)` registers a versioned dataset | Recommended for production and CI/CD; small sets can be passed inline (`file_content`) |
| Synthetic generation (preview) | **Simple QnA** produces `query` and `ground_truth` pairs; **Simulation seed** produces scenario descriptions for multi-turn simulation. Sources: an agent definition, a prompt, or a reference file | `max_samples` from 15 to 1,000; generator is an Azure OpenAI deployment that supports the Responses API; start with 15 and review |
| Production traces | **Data Generation**, Create dataset, From traces, or Add to dataset from the trace view | `max_samples` 1 to 1,000; private content redacted by default; the project's managed identity needs Reader on the connected Application Insights resource; wait for trace ingestion (30 to 90 seconds) |

A good dataset covers typical questions, edge cases, questions whose answer isn't in the sources (the expected behavior is a refusal) and adversarial inputs. Pin the agent version when you build a dataset from traces, regenerate synthetic data when instructions change significantly, and combine synthetic and trace-based rows.

> **Exam trap.** If an evaluator returns an error about a missing input, the dataset isn't necessarily wrong: the mapping is. A file with a `question` column needs `"query": "{{item.question}}"`. And a target-based run needs `include_sample_schema=True` before `{{sample.output_text}}` can be mapped.

## Quality metrics: groundedness, relevance, coherence and fluency

AI-assisted quality evaluators use an LLM as judge: you pass a model deployment (Learn recommends `gpt-5-mini` for balance of performance and cost) and each call consumes tokens.

| Evaluator | Identifier | Question it answers | Output |
| --- | --- | --- | --- |
| Groundedness | `builtin.groundedness` | Is every claim of the response supported by the provided context? | 1 to 5, pass at 3 or more by default |
| Relevance | `builtin.relevance` | Does the response address the query? | 1 to 5, default threshold 3 |
| Coherence | `builtin.coherence` | Are the ideas logically organized and connected? | 1 to 5, default threshold 3 |
| Fluency | `builtin.fluency` | Is the language grammatical and readable? | 1 to 5, default threshold 3 |
| Retrieval | `builtin.retrieval` | Did the retrieved context contain what the query needed? | 1 to 5, default threshold 3 |
| Response completeness (preview) | | Does the response include the critical information of the ground truth? | 1 to 5, default threshold 3 |
| Groundedness Pro (preview) | | Is the response grounded, as judged by Azure AI Content Safety, with no model deployment? | Pass or fail |
| Document retrieval | `builtin.document_retrieval` | Are the retrieved documents the right ones, against labeled relevance? | Several ranking metrics |
| Similarity | `builtin.similarity` | AI-assisted closeness to the ground truth (needs a judge deployment) | 1 to 5, default threshold 3 |
| F1, BLEU, GLEU, ROUGE, METEOR | `builtin.f1_score`... | Token or n-gram overlap with the ground truth, computed without a judge model | 0 to 1, default threshold 0.5 |

Each result includes a score, a label, the reason and the threshold:

```json
{
  "type": "azure_ai_evaluator",
  "name": "Coherence",
  "metric": "coherence",
  "score": 4,
  "label": "pass",
  "reason": "The response directly addresses the question with clear, logical connections between ideas.",
  "threshold": 3,
  "passed": true
}
```

| Symptom | Metric that detects it |
| --- | --- |
| The answer contains facts that aren't in the retrieved documents (hallucination) | Groundedness |
| The answer is accurate but doesn't answer what was asked | Relevance |
| The retriever returns the wrong chunks | Retrieval, document retrieval |
| The answer jumps between ideas, contradicts itself | Coherence |
| Grammar and readability are poor | Fluency |
| The answer misses key facts of the expected answer | Response completeness, similarity, F1 |

Coherence and fluency currently support English responses only, and scores are less reliable for very short responses. Coherence can also be evaluated at **conversation** level (`evaluation_level="conversation"`), which requires the `messages` format; the default level is `turn`.

> **Exam trap.** Groundedness and relevance measure different things. A response copied from the context is perfectly grounded even if it doesn't answer the question (low relevance); a correct answer from the model's general knowledge is relevant but ungrounded if the context doesn't contain it. Groundedness judges the response against `context`; relevance doesn't use it.

## Risk and safety evaluations

Risk and safety evaluators run on the hosted Foundry evaluation service, not on your model deployment: they need **no `deployment_name`**, but they need your Foundry project, in a region that supports them.

| Evaluator | Detects | Inputs |
| --- | --- | --- |
| `builtin.violence`, `builtin.sexual`, `builtin.self_harm`, `builtin.hate_unfairness` | Harmful content, with a severity score | `query`, `response` or `messages` |
| `builtin.protected_material` | Copyrighted or protected text, classified by the Azure AI Content Safety protected material service | `query`, `response` or `messages` |
| `builtin.indirect_attack` | The response followed instructions injected through retrieved content (XPIA): manipulated content, intrusion, information gathering | `query`, `response` or `messages`; models only, not agents |
| `builtin.code_vulnerability` | Security issues in generated code (SQL injection, hard-coded credentials, weak cryptography...) for Python, Java, C++, C#, Go, JavaScript and SQL | `query`, `response` or `messages` |
| `builtin.ungrounded_attributes` | Emotional state or protected-class attributes inferred about a person and not grounded in the context | `query`, `response`, `context` |
| `builtin.prohibited_actions`, `builtin.sensitive_data_leakage` (preview) | An agent performing disallowed actions or exposing sensitive data | `query`, `response`, `tool_calls`; agent targets only |

The four content safety evaluators score severity from 0 to 7:

| Severity | Score |
| --- | --- |
| Very low | 0 to 1 |
| Low | 2 to 3 |
| Medium | 4 to 5 |
| High | 6 to 7 |

With the default threshold of 3, a result **passes when the score is at most the threshold** and fails above it. The other risk evaluators return pass or fail directly (ungrounded attributes returns a true or false label: true when an attribute is detected and ungrounded). Across a run, look at the share of rows that fail.

```text
testing_criteria = [
    {
        "type": "azure_ai_evaluator",
        "name": "violence",
        "evaluator_name": "builtin.violence",
        "data_mapping": {"query": "{{item.query}}", "response": "{{item.response}}"},
    },
    {
        "type": "azure_ai_evaluator",
        "name": "indirect_attack",
        "evaluator_name": "builtin.indirect_attack",
        "data_mapping": {"query": "{{item.query}}", "response": "{{item.response}}"},
    },
]
```

Safety evaluations need inputs that try to provoke harm: include adversarial queries in the dataset, use simulated conversations, or run **AI red teaming** for automated adversarial testing.

> **Exam trap.** Guardrails (content filters) block harmful content at run time; safety evaluators measure how often the application produces it on a test set. And the direction is reversed compared with quality metrics: a high quality score is good, a high severity score is bad, and passing means the severity is at or below the threshold.

## Automated evaluation workflows with built-in and custom evaluators

A **cloud evaluation** with the Foundry SDK (`azure-ai-projects`) has three steps: define the data schema and the testing criteria, create the evaluation, start a run on a dataset or a target. Results stay in the project, appear in the portal and can be routed to Application Insights.

```text
from azure.identity import DefaultAzureCredential
from azure.ai.projects import AIProjectClient

project_client = AIProjectClient(endpoint=endpoint, credential=DefaultAzureCredential())
openai_client = project_client.get_openai_client()

data_id = project_client.datasets.upload_file(
    name="support-eval", version="3", file_path="./evals/support.jsonl"
).id

eval_object = openai_client.evals.create(
    name="support-quality",
    data_source_config={
        "type": "custom",
        "item_schema": {
            "type": "object",
            "properties": {"query": {"type": "string"}, "context": {"type": "string"}},
            "required": ["query"],
        },
        "include_sample_schema": True,
    },
    testing_criteria=[
        {
            "type": "azure_ai_evaluator",
            "name": "groundedness",
            "evaluator_name": "builtin.groundedness",
            "initialization_parameters": {"deployment_name": "eval-judge"},
            "data_mapping": {"context": "{{item.context}}", "response": "{{sample.output_text}}"},
        },
        {
            "type": "azure_ai_evaluator",
            "name": "violence",
            "evaluator_name": "builtin.violence",
            "data_mapping": {"query": "{{item.query}}", "response": "{{sample.output_text}}"},
        },
    ],
)

run = openai_client.evals.runs.create(
    eval_id=eval_object.id,
    name="support-agent-v4",
    data_source={
        "type": "azure_ai_target_completions",
        "source": {"type": "file_id", "id": data_id},
        "input_messages": {
            "type": "template",
            "template": [
                {"type": "message", "role": "user",
                 "content": {"type": "input_text", "text": "{{item.query}}"}}
            ],
        },
        "target": {"type": "azure_ai_agent", "name": "support-agent", "version": "4"},
    },
)
```

| Element | Meaning |
| --- | --- |
| `data_source` type `jsonl` or `csv` with `file_id` | Evaluate rows that already contain the responses |
| `azure_ai_target_completions` | Generate responses during the run from `input_messages`, for a target of type `azure_ai_model` or `azure_ai_agent` (version optional; latest if omitted) |
| `initialization_parameters` | Judge deployment for AI-assisted evaluators, thresholds for custom ones |
| Role | Foundry User on the project, and at the Foundry resource (account) scope when the run calls a model deployment such as the judge (a project-only assignment doesn't authorize inference); with bring-your-own storage, the project's managed identity needs Storage Blob Data Contributor on the storage account |

**Custom evaluators** (preview) are registered in the project's evaluator catalog and used in `testing_criteria` like built-in ones:

| Type | Definition | Score |
| --- | --- | --- |
| Code-based | A Python function `grade(sample, item)` returning a float; requires `pass_threshold` | 0.0 to 1.0, higher is better |
| Prompt-based (LLM judge) | A judge prompt with `{{response}}`-style variables that returns JSON with `result` and `reason`; requires `threshold` | Ordinal (for example 1 to 5), continuous or binary |
| Endpoint-based | Your HTTP endpoint receives the data and returns scores within 30 seconds | Defined by the endpoint |

```text
def grade(sample: dict, item: dict) -> float:
    response = item.get("response", "")
    if not response:
        return 0.0
    return 1.0 if "order number" in response.lower() else 0.0
```

Code-based evaluators run in a sandbox: code under 256 KB, 2 minutes per grading call, **no network access**, preinstalled packages only (numpy, pandas, scikit-learn, rapidfuzz, nltk, rouge-score...). An exception or a timeout records 0.0 for the row and flags it as an error. Register them with `project_client.beta.evaluators.create_version(...)`.

**Local evaluation** with the Azure AI Evaluation SDK (`pip install azure-ai-evaluation`, documented for Foundry classic and in preview) runs evaluator classes such as `GroundednessEvaluator(model_config)` or `ContentSafetyEvaluator(credential=..., azure_ai_project=...)` through `evaluate(data="data.jsonl", evaluators={...}, evaluator_config={...}, azure_ai_project=..., output_path=...)`; passing `azure_ai_project` logs the results to the project.

**Automating** the evaluation:

| Trigger | Tool |
| --- | --- |
| Pull request that changes a prompt or an agent | `microsoft/ai-agent-evals@v3-beta` GitHub Action (preview): inputs `azure-ai-project-endpoint`, `deployment-name` (judge), `agent-ids` (`name:version`, comma-separated), `data-path` (JSON file with `name`, `evaluators`, `data`); results with confidence intervals in the run summary |
| Blocking quality gate | The azd evaluation extension (preview) with a failure threshold such as `--fail-on pass-rate=0.8` |
| Before promotion to the next environment | A pipeline stage that runs the cloud evaluation and compares with the baseline run |
| After release | Continuous evaluation of sampled production traffic and scheduled runs on the same dataset (see the observability chapter) |

The workflow authenticates with OIDC (`permissions: id-token: write`, `azure/login`) and needs Foundry User on the project, or on the Foundry resource when the run calls a judge deployment. Evaluations cost judge tokens: don't run them on every commit.

> **Exam trap.** A code-based custom evaluator can't call an external API or a model: the sandbox has no network. To judge with a model, write a prompt-based evaluator; to reach your own service, use an endpoint-based evaluator.

<!-- section: key-points -->
## Key points

- Dataset: JSONL or CSV with `query`, `response`, `context`, `ground_truth`, or `messages`; versioned with `datasets.upload_file`; synthetic (15 to 1,000 samples, preview) or from traces.
- Mapping: `{{item.field}}` for dataset fields, `{{sample.output_text}}` and `{{sample.output_items}}` for target outputs (with `include_sample_schema=True`); local SDK uses `${data.field}` and `${outputs.field}`.
- Quality: groundedness (judged against the context), relevance, coherence, fluency, retrieval; 1 to 5, pass at 3 or more, LLM judge deployment required.
- Safety: hosted service, no deployment name, project required; severity 0 to 7, pass at 3 or less; protected material, indirect attack, code vulnerability give pass or fail.
- Automation: `evals.create` plus `evals.runs.create`, custom code (no network) or prompt-based evaluators, GitHub Action `ai-agent-evals` with baseline comparison, gates on pass rate.
