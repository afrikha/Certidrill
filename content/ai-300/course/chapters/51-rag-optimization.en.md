A retrieval-augmented generation (RAG) application is only as good as the passages it retrieves: a perfect model grounded on the wrong chunks gives a fluent, wrong answer. Optimizing RAG means tuning the retrieval pipeline (chunk size, overlap, number of candidates, thresholds, filters, query rewriting), choosing the right embedding model, combining keyword and vector search with a reranker, and proving every change with metrics before it reaches all users. The examples use Azure AI Search, the retrieval engine of Microsoft Foundry. Exam questions describe a retrieval symptom and ask which parameter, model, query shape or metric fixes or measures it.

## Tuning chunks, thresholds and retrieval strategies

**Chunking** splits documents before they are embedded. Reasons: embedding models have an input limit (8,191 tokens for `text-embedding-3-small`, about 6,000 words), truncation loses content, and a long document that covers several subtopics is poorly represented by one vector.

| Technique | How | Built-in option |
| --- | --- | --- |
| Fixed-size | Same length with 10 to 15 % overlap (for example 200 words or 600 characters) | Text Split skill, `textSplitMode: pages` |
| Variable-size | Split on sentences, line ends or Markdown and HTML headings | Text Split skill, `textSplitMode: sentences`; Content Understanding skill |
| Semantic | Keep related sentences and paragraphs together, even across pages | Content Understanding skill (Markdown output) |
| Custom | Mix approaches, or add the document title to each chunk | Custom skill |

Microsoft's starting point is **512 tokens (about 2,000 characters) with 25 % overlap (128 tokens)**. Structured data may need less overlap, narrative or conversational text more. With the Text Split skill, the recommended character-based default is:

```json
{
  "@odata.type": "#Microsoft.Skills.Text.SplitSkill",
  "textSplitMode": "pages",
  "maximumPageLength": 2000,
  "pageOverlapLength": 500,
  "maximumPagesToTake": 0,
  "inputs": [ { "name": "text", "source": "/document/content" } ],
  "outputs": [ { "name": "textItems", "targetName": "pages" } ]
}
```

`pageOverlapLength` must be **less than half** of `maximumPageLength`; `maximumPagesToTake` 0 takes all chunks. Smaller chunks and more overlap produce more chunks (more storage, more embedding cost). Choose a size that suits every model in the pipeline, for example the embedding model and the chat model.

**How many results.** Vector queries return `k` nearest neighbors, `top` sets how many results a hybrid query returns, and both default to **50** when unset. A balanced pattern is `k` 30 to 50 and `top` 10 to 20. Microsoft's recommended pipeline: retrieve broadly (20 to 50 candidates), merge with RRF, rerank, then keep the top 5 or 10 for generation. Retrieval optimizes **recall**, reranking optimizes **precision**.

**Similarity thresholds** drop weak matches from pure vector queries (preview, `api-version=2026-08-01-preview`):

```json
{
  "vectorQueries": [
    {
      "kind": "vector",
      "vector": [0.012, -0.044, 0.031],
      "fields": "contentVector",
      "k": 10,
      "threshold": { "kind": "vectorSimilarity", "value": 0.8 }
    }
  ]
}
```

Results below the value are excluded even if fewer than `k` remain, and filtering happens before fusion. Thresholds aren't suited to hybrid queries, whose RRF scores are small and volatile. Semantic reranker scores also vary slightly between runs, so avoid very granular thresholds on them.

**Other levers:**

| Lever | Effect |
| --- | --- |
| HNSW (`m`, `efConstruction`, `efSearch`) vs exhaustive KNN | HNSW is approximate and fast; exhaustive KNN scans every vector (`"exhaustive": true` per query). Higher `efSearch` and `efConstruction` improve recall at the cost of latency and compute |
| Similarity metric | `cosine` for Azure OpenAI embedding models |
| Filters on keyword or entity fields | Remove irrelevant documents; `vectorFilterMode` is `preFilter` (default), `postFilter` (may return fewer than `top`) or `strictPostFilter` (preview) |
| Query rewriting | Fixes vague queries, missing keywords and extra words |
| Query decomposition | Splits a complex question into subqueries, each retrieved separately |
| Query augmentation | Adds context to a short query without changing its meaning |
| HyDE | Embeds a hypothetical answer generated by a model, for answer-to-answer similarity |

| Symptom | Likely fix |
| --- | --- |
| Answer misses details split across two chunks | More overlap or larger chunks |
| Chunks mix several topics, retrieval is vague | Smaller or semantic chunks |
| Irrelevant passages reach the prompt | Fewer final results after reranking, a vector threshold, or filters |
| The right document is never in the candidates | Larger `k`, hybrid search, query rewriting |
| Multi-part questions answered partly | Query decomposition |

> **Exam trap.** A vector `threshold` belongs on a single pure vector query. On a hybrid query the fused `@search.score` is an RRF score, not a similarity, so a 0.8 cut-off would remove everything. To drop weak hybrid results, rerank and keep the top N.

## Selecting and fine-tuning embedding models

The **same embedding model** must embed the chunks and the queries; the vector field's dimensions must equal the model's output. Changing the model therefore means re-embedding the whole index.

| Model | Dimensions | Notes |
| --- | --- | --- |
| `text-embedding-ada-002` | 1536 (fixed) | Older generation |
| `text-embedding-3-small` | 1 to 1536 | Default 1536, lower cost |
| `text-embedding-3-large` | 1 to 3072 | Default 3072, higher accuracy, more storage |

`dimensions` shortens the output of the text-embedding-3 models; set the same value on the index field. In an indexer pipeline, the **Azure OpenAI Embedding skill** calls the deployment:

```json
{
  "@odata.type": "#Microsoft.Skills.Text.AzureOpenAIEmbeddingSkill",
  "resourceUri": "https://contoso-foundry.openai.azure.com/",
  "deploymentId": "text-embedding-3-large",
  "modelName": "text-embedding-3-large",
  "dimensions": 1024,
  "inputs": [ { "name": "text", "source": "/document/pages/*" } ],
  "outputs": [ { "name": "embedding" } ]
}
```

With no `apiKey` or `authIdentity`, the skill uses the search service's system-assigned identity, which needs **Cognitive Services OpenAI User** on the model resource. The skill accepts at most 8,000 tokens of text (split first). The embeddings API accepts up to 8,192 tokens per input, 2,048 inputs per request and 300,000 tokens per request in total.

Selection flow from the Azure Architecture Center:

1. Can you find your entities and keywords on the internet? Then a **general model** probably knows them: start with the top-ranked models of the MTEB leaderboard and test them on your data.
2. Specialized domain: look for a **domain model** (for example a biomedical embedding model) and test it.
3. No domain model, or it performs poorly: **fine-tune a general model** on your vocabulary. Fine-tuning adjusts the weights to represent your terms, and helps specialized domains such as code search or legal documents; poor training data can degrade results, so evaluate carefully, and first check whether prompt engineering solves the problem.
4. Always verify the license and the languages supported.

Why vocabulary matters: a word outside the model's vocabulary is split into subwords (*histamine* into *his*, *ta*, *mine*), which gives a poorer vector match. Compare candidates by **retrieval tests on real queries**: embed the content, run the queries, check whether the right chunks come back. Benchmarks are often academic datasets that don't reflect business data, and a larger model isn't always better: more dimensions mean more storage, compute and latency.

| Requirement | Choice |
| --- | --- |
| Lowest cost and storage, general content | `text-embedding-3-small`, or fewer dimensions |
| Highest accuracy on general content | `text-embedding-3-large` |
| Domain jargon the general models miss | A domain model, else a fine-tuned general model |
| Images or diagrams | Convert to text with Content Understanding, then embed with a text model |

> **Exam trap.** Embedding queries with a different model, or a different `dimensions` value, than the indexed chunks silently breaks vector search. Upgrading the embedding model is a full re-indexing project, not a configuration change of the query.

## Implementing and tuning hybrid search

A **hybrid query** is one request with both `search` (full-text, BM25) and `vectorQueries` (HNSW or exhaustive KNN). Both run in parallel and **Reciprocal Rank Fusion** merges them: each document gets `1/(rank + k)` per result list, with a small constant such as 60, and the scores are summed. Vector search finds conceptually similar passages without shared words; keyword search wins on **product codes, specialized jargon, dates and people's names**, where exact matches matter. Microsoft reports that hybrid retrieval with semantic ranker offers significant relevance benefits on real-world and benchmark datasets.

```json
{
  "search": "error E-4417 on the Fabrikam T200 printer",
  "vectorQueries": [
    {
      "kind": "text",
      "text": "error E-4417 on the Fabrikam T200 printer",
      "fields": "contentVector",
      "k": 50,
      "weight": 1.5
    }
  ],
  "filter": "productLine eq 'printers'",
  "queryType": "semantic",
  "semanticConfiguration": "support-semantic",
  "captions": "extractive",
  "select": "title, content, source",
  "top": 10
}
```

One vector query can target up to 10 vector fields (`"fields": "contentVector, titleVector"`), all embedded with the same model. `kind: text` needs a **vectorizer** on the vector field; otherwise send `kind: vector` with an embedding computed by the same model.

| Score | Algorithm | Range |
| --- | --- | --- |
| `@search.score`, full-text | BM25 | No upper limit |
| `@search.score`, vector | Similarity | 0.333 to 1.00 for cosine |
| `@search.score`, hybrid | RRF | Small, bounded by the number of fused queries |
| `@search.rerankerScore` | Semantic ranker | 0.00 to 4.00 |

Tuning knobs:

| Knob | Default | Effect |
| --- | --- | --- |
| `weight` on a vector query | 1.0 | Above 1 favors the vector side in RRF, below 1 favors keywords; must be greater than zero |
| `k` | 50 if unset | Vector candidates; use 50 with semantic ranker, which reranks at most 50 |
| `hybridSearch.maxTextRecallSize` (preview) | 1,000 (max 10,000) | BM25 results sent to RRF |
| `hybridSearch.countAndFacetMode` (preview) | `countAllResults` | `countRetrievableResults` counts only documents that were ranked |

The **semantic ranker** runs after RRF on the top 50 results and uses only text from the semantic configuration: `title` and `keywords` up to 128 tokens each, then `content`, for at most 2,000 tokens per document (put the most important fields first). It returns `@search.rerankerScore` (4 = answers the question completely, 0 = irrelevant), plus verbatim captions and optional answers; it never generates text. It's billed per query when `queryType` is `semantic` and the search string isn't empty.

> **Exam trap.** Don't add `orderby` to a hybrid query: an explicit sort replaces relevance ranking. And don't compare a hybrid `@search.score` (about 0.03) with a BM25 or cosine score: use `@search.rerankerScore` when you need an absolute relevance scale.

## Evaluating and improving RAG with relevance metrics and A/B tests

Measure retrieval and generation separately: otherwise you can't tell whether a bad answer comes from the retriever or from the model.

| Metric | Measures | Needs |
| --- | --- | --- |
| Precision at K | Share of relevant items in the top K | Relevance labels |
| Recall at K | Share of all relevant items found in the top K | Relevance labels |
| Mean reciprocal rank (MRR) | Average of 1/rank of the first relevant result | Relevance labels |
| **Document Retrieval** (`builtin.document_retrieval`) | NDCG@3, XDCG@3, Fidelity, top-1 relevance, top-3 max relevance, holes | `retrieval_ground_truth` (labels per document) and `retrieved_documents`; no judge model |
| **Retrieval** (`builtin.retrieval`) | Relevance of the retrieved context to the query, 1 to 5 | `query`, `context`, a judge deployment; no ground truth |
| **Groundedness** (`builtin.groundedness`) | Response supported by the context (precision) | `response`, `context` (and `query`) |
| **Relevance** (`builtin.relevance`) | Response answers the query | `query`, `response` |
| **Response Completeness** (preview) | Response covers the ground truth (recall) | `response`, `ground_truth` |

Score-based evaluators pass at 3 or above on the 1 to 5 scale by default. **Holes** counts retrieved documents with no relevance label: a high value means the labels must be completed before trusting NDCG. Document Retrieval is designed for **parameter sweeps** across search modes, `top_k` and chunk sizes:

```text
testing_criteria = [
    {
        "type": "azure_ai_evaluator",
        "name": "document_retrieval",
        "evaluator_name": "builtin.document_retrieval",
        "initialization_parameters": {
            "ground_truth_label_min": 0,
            "ground_truth_label_max": 4,
        },
        "data_mapping": {
            "retrieval_ground_truth": "{{item.retrieval_ground_truth}}",
            "retrieved_documents": "{{item.retrieved_documents}}",
        },
    },
]
```

Test **positive queries** (the data contains the answer: metrics should approach 1) and **negative queries** (it doesn't: retrieval should approach 0 and the assistant should say it doesn't know).

| Results | Diagnosis |
| --- | --- |
| Low retrieval, low groundedness | Retrieval problem: chunking, embeddings, hybrid, `k` |
| High retrieval, low groundedness | Generation problem: prompt, model, too much context |
| High groundedness, low completeness | Relevant chunks missing from the top K, or answer too short |
| High NDCG, low Fidelity | Good ranking, but many known-good documents never retrieved |

**A/B testing** compares a baseline with a variant:

1. Set the **decision criteria before** running (for example a minimum average score and a cost or latency ceiling), so results can't be rationalized afterward.
2. Change **one variable at a time** (chunk size, embedding model, weight, reranker, prompt); with several changes you can't tell which one caused the difference.
3. Run both variants against the **same test dataset** and evaluators, recording quality, tokens and latency.
4. Select both runs in Foundry and choose **Compare**, with the baseline set: each cell shows a **t-test** result (ImprovedStrong at p 0.001 or less, ImprovedWeak up to 0.05, Inconclusive with too few examples or p 0.05 and above), with sample size and p-value on hover. The comparison view isn't saved.
5. For an online test, route a share of live traffic to the variant (for example weighted backends in API Management) and watch continuous evaluation, latency and token metrics per variant before a full rollout.

> **Exam tip.** "Is the new chunk size better, or is it noise?" → compare the two evaluation runs and read the statistical significance. "Inconclusive" means more test rows are needed, not that the variants are equal.

## Key points

- Start chunking at 512 tokens with 25 % overlap (Text Split: 2,000 and 500 characters); overlap under half the page length.
- Retrieve 20 to 50 candidates, merge with RRF, rerank, keep 5 to 10; `k` and `top` default to 50.
- Vector `threshold` (preview, `vectorSimilarity`) is for pure vector queries, not hybrid.
- Same embedding model and dimensions for chunks and queries; a model change means re-embedding.
- text-embedding-3-small up to 1536 dimensions, 3-large up to 3072; general model, then domain model, then fine-tuning.
- Hybrid = BM25 + vectors fused by RRF (constant about 60); keywords win on codes, names, dates and jargon; semantic ranker reranks the top 50 (0 to 4).
- Evaluate retrieval (Document Retrieval, Retrieval) separately from generation (groundedness, relevance, completeness).
- A/B: criteria first, one change at a time, same dataset, Compare with t-test significance.
