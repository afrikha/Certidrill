Fine-tuning changes a model's weights by training it further on task-specific examples, instead of adding examples to every prompt. In Microsoft Foundry it can improve accuracy beyond what fits in a prompt, shorten prompts (lower token cost and latency), enforce a style or schema, improve tool selection and arguments, teach a model to use retrieved context, and specialize a smaller model with examples generated by a larger one. It doesn't replace retrieval for current information, nor application-level safety controls, and its benefits aren't guaranteed: always compare the result with the baseline on held-out data. Exam questions ask which method fits a requirement, how to produce training data, how to read training metrics and which deployment type to use at each stage.

## Designing and implementing fine-tuning methods

Foundry offers **Managed Training** (you submit data and settings, Foundry runs the job; recommended to start) and **Programmed Training** (preview, by approval: you write the Python training loop and control losses, rewards and checkpoints). Managed Training has three methods:

| Method | Training signal | Choose it when | Examples of supported models |
| --- | --- | --- | --- |
| **SFT** (supervised fine-tuning) | Prompts with the desired responses | You can demonstrate the expected behavior: format, style, domain answers, tool calls | `gpt-4o-mini`, `gpt-4o`, `gpt-4.1`, `gpt-4.1-mini`, `gpt-4.1-nano` |
| **DPO** (direct preference optimization) | A preferred and a rejected response to the same input | Quality is a matter of preference: tone, completeness, helpfulness | `gpt-4o`, `gpt-4.1`, `gpt-4.1-mini`, `gpt-4.1-nano` |
| **RFT** (reinforcement fine-tuning) | Prompts plus a **grader** that scores generated responses | Several good answers exist and you can score them reliably (reasoning tasks) | `o4-mini` (`gpt-5` by invitation) |

SFT training data is JSON Lines in the Chat Completions `messages` format; DPO lines have `input`, `preferred_output` and `non_preferred_output`:

```json
{"messages": [{"role": "system", "content": "You classify Contoso insurance claims."}, {"role": "user", "content": "Water damage in the kitchen after a pipe burst."}, {"role": "assistant", "content": "{\"category\": \"property\", \"priority\": \"high\"}"}]}
{"input": {"messages": [{"role": "user", "content": "Summarize policy P-118 for a customer."}]}, "preferred_output": [{"role": "assistant", "content": "Your policy covers water damage up to 10,000 USD after a 250 USD deductible."}], "non_preferred_output": [{"role": "assistant", "content": "See the policy document."}]}
```

RFT records end with a `user` message and carry the fields the grader reads (for example `reference_answer`). Grader types:

| Grader | Use |
| --- | --- |
| `string_check` | Exact labels or substrings (`eq`, `ne`, `like`, `ilike`) |
| `text_similarity` | Similarity to a reference (`fuzzy_match`, `bleu`, `rouge_l`...) |
| `score_model` | A grading model applies a rubric within a `range` |
| `python` | A `grade(sample, item)` function returns a score; runs without network access |
| `multi` | Combines child graders with a `calculate_output` formula |

```json
{
  "name": "claim_category_grader",
  "type": "string_check",
  "input": "{{item.reference_answer}}",
  "reference": "{{sample.output_text}}",
  "operation": "eq"
}
```

Training types trade cost against residency:

| Training type | Characteristics |
| --- | --- |
| Standard | Trains in the resource's region, data residency guaranteed |
| Data zone | Within a data zone (US only) |
| Global | Cheaper, shorter queues, data and weights copied outside your region: no residency guarantee |
| Developer | Lowest cost on idle capacity, preemptible (paused jobs resume, not billed while paused), no SLA or residency: for experiments |

Create a job with the OpenAI client of the project (training needs **Foundry User**; deploying needs **Foundry Owner**):

```text
training_file = client.files.create(file=open("train.jsonl", "rb"), purpose="fine-tune")
validation_file = client.files.create(file=open("valid.jsonl", "rb"), purpose="fine-tune")
client.files.wait_for_processing(training_file.id)
client.files.wait_for_processing(validation_file.id)

job = client.fine_tuning.jobs.create(
    model="gpt-4.1-mini",
    training_file=training_file.id,
    validation_file=validation_file.id,
    suffix="claims-v1",
    method={
        "type": "supervised",
        "supervised": {"hyperparameters": {
            "n_epochs": "auto", "batch_size": "auto", "learning_rate_multiplier": "auto"}},
    },
    extra_body={"trainingType": "GlobalStandard"},
)
```

Hyperparameters accept a number or `auto`; keep the model's defaults for the first job and change them only after comparing validation results. DPO uses `method={"type": "dpo"}` and RFT `method.reinforcement`. Methods chain: to run DPO on an SFT result, pass the **fine-tuned model identifier**, not its deployment name. **Distillation** is SFT on responses generated by a larger teacher model, to make a smaller model reach the quality target at lower cost and latency.

> **Exam trap.** Match the data to the method: demonstrations → SFT, pairs of better and worse answers → DPO, a scoring function → RFT. And if answers must reflect documents that change every week, fine-tuning is the wrong tool: use RAG, which the fine-tuned model can still consume.

## Creating and managing synthetic data for fine-tuning

When real examples are scarce or sensitive, **synthetic data generation** (preview) turns one reference file into training data, in the Foundry portal under Data, **Data Generation (preview)**, Create dataset, Generate synthetic data.

| Generator | Reference file | Produces | Parameter |
| --- | --- | --- | --- |
| **Simple Q&A** | PDF, Markdown or text, under 20 MB | Question and answer pairs from a domain document | Question type: Long answer (analytical) or Short answer (factual) |
| **Tool use** | OpenAPI 3.0.x or 3.1.x specification in JSON, under 20 MB | Multi-turn conversations with `tool_calls` and `tool` messages, plus a `tools` array | None |

Wizard choices: task type, parameters, reference file (**one file only**: merge several documents first), number of samples (**50 to 1,000**), the **generator model** (deployed automatically if needed), an optional **80/20 train and validation split**, and a name suffix. The job's preview panel shows sample outputs and cost; the output is **JSONL** in the `messages` format, downloadable or usable directly with **Use this dataset**. Prerequisites: Foundry User (or Foundry Project Manager) and a supported region; deploying a generator model needs Foundry Owner.

Quality rules:

- Clean the reference: remove boilerplate such as navigation menus, and remove personal and sensitive data.
- For tool use, describe every API path and parameter clearly and put business policies in the path descriptions.
- **Start small**: generate a sample, review it (generated conversations can contain inconsistencies, such as amounts that don't add up), adjust, then scale.
- **Mix** synthetic data with a portion of real data to generalize better; a smaller learning rate limits overfitting on synthetic data, and an earlier checkpoint can help if the model regresses.
- Keep **validation and test data separate** from training data, and audit the fine-tuned model for biases introduced by synthetic data.

Production also feeds datasets: **traces to dataset** builds a versioned **evaluation** dataset from an agent's traces (Data Generation, Create dataset, From traces). `max_samples` (1 to 1,000) turns on intelligent sampling that drops low-signal traces and picks diverse ones; `redact_private_content` is on by default; pin `agent_version`; write mode `OVERWRITE` (default, next version with only new rows) or `MERGE`. The project's managed identity needs **Reader** on the Application Insights resource.

```text
job = EvaluationDataGenerationJobInputs(
    name="claims-agent-eval",
    sources=[TracesDataGenerationJobSource(
        agent_name="claims-agent", agent_version="4",
        start_time=end_time - timedelta(days=7), end_time=end_time)],
    generation_configuration=TracesDataGenerationJobConfiguration(
        max_samples=200, redact_private_content=True),
    output_configuration=EvaluationDataGenerationJobOutputConfiguration(
        name="claims-agent-eval", write_mode=DataGenerationJobOutputWriteMode.MERGE),
)
poller = project_client.datasets.begin_create_generation_job(job=job)
```

> **Exam trap.** Synthetic data from one document covers that document only: it multiplies examples, it doesn't add knowledge the reference lacks. Generated rows must be reviewed before training, and a test set generated from the same file as the training set inflates scores (evaluation leakage).

## Monitoring and optimizing fine-tuned model performance

During training, a job reports metrics per step and may return a CSV results file:

| Method | Metrics |
| --- | --- |
| SFT | `train_loss`, `full_valid_loss`, `train_mean_token_accuracy`, `full_valid_mean_token_accuracy` |
| RFT | `train_reward_mean`, `valid_reward_mean`, per-grader scores, reasoning tokens means, grader errors |
| DPO | Validation on held-out preference examples; token accuracy doesn't measure preference alignment |

| Pattern | Meaning | Action |
| --- | --- | --- |
| Training loss falls, validation loss rises | Overfitting | Pick an earlier checkpoint, fewer epochs, smaller learning rate, more diverse data |
| Both losses stay high | Not learning the task | Check data quality and consistency, more examples |
| Reward rises, held-out quality doesn't | **Reward hacking**: the model exploits the grader | Test the grader on correct, wrong and adversarial answers; combine graders |
| Combined reward high, one criterion poor | A `multi` grader hides a weak component | Read per-grader scores |

**Checkpoints** appear as training progresses. Don't assume the latest is the best: compare candidates on held-out tasks, never on training loss alone. Then evaluate the chosen model against the **baseline** (the base model with your best prompt) using the same dataset and evaluators, and compare the runs. A fine-tuned model that doesn't beat the baseline isn't worth its hosting cost.

In production, a fine-tuned deployment has the same Azure Monitor metrics as any deployment (latency, tokens, requests) and can be covered by continuous evaluation. Reassess when the data changes or the base model nears retirement.

Training cost:

| Method | Billing |
| --- | --- |
| SFT | Training tokens x epochs x price per token |
| DPO | Training tokens |
| RFT | Training hours plus grader inference tokens (if a model grader is used) |

Not billed: queue time, failed jobs, jobs canceled before training starts, data safety checks. An RFT job has a **spending limit**: when reached, training pauses and creates a deployable checkpoint; resuming continues without another limit. To reduce cost: short first runs, fewer validation samples, the smallest adequate grader, Global training when residency isn't required, early cancellation of runs that don't improve the target metric, and budget alerts in Cost Management. The `FineTunedTrainingHours` metric tracks training hours.

> **Exam trap.** A lower training loss isn't proof of a better model. The exam's right answer for "which checkpoint should you deploy" is the one that scores best on the **validation or held-out evaluation**, which is often not the final one.

## Managing a fine-tuned model from development to production

1. **Prepare** separate training, validation and test sets.
2. **Train** with the right method and training type; choose a `suffix` that identifies the version.
3. **Select a checkpoint** on validation results.
4. **Evaluate** on a **Developer** deployment: test in the Playground (select the fine-tuned deployment, not the base model) and run cloud evaluations against the baseline.
5. **Deploy to production** on a serverless Standard, Global Standard or provisioned deployment, within quota.
6. **Monitor** metrics and continuous evaluation; **iterate** (for example DPO on top of the SFT model) and **retire**: delete deployments you no longer need.

| Deployment type | Billing | Use |
| --- | --- | --- |
| Developer | Tokens at Global Standard rates, **no hourly hosting fee** | Evaluation only: **removed after 24 hours**, no SLA, no residency |
| Standard | Tokens plus an **hourly hosting fee** | Regional production with residency |
| Global Standard | Tokens plus hourly hosting fee | Production on global capacity (weights may be stored outside your geography) |
| Provisioned Throughput | PTU-hours, no per-token charge | High, steady volume |
| Global Provisioned | PTU-hours | Imported custom models |

| Deployment option | Status | Notes |
| --- | --- | --- |
| Serverless | GA | Foundry hosts the model; deploy from the job's details, Deploy, Serverless |
| Managed compute | Preview | Dedicated GPUs run a LoRA-enabled base deployment with one or more matching **LoRA adapters**; billed per GPU-hour, even without requests |
| Fireworks on Foundry | Preview | One adapter merged into a full copy of the base model; a Subscription Owner or Contributor enables it |

Deploying requires **Foundry Owner** or a role with `Microsoft.CognitiveServices/accounts/deployments/write`. Standard serverless deployments of fine-tuned models exist only in some regions (East US 2, North Central US, Sweden Central depending on the model). An adapter only fits the exact base model and version it was trained on.

For a new version, deploy it as a separate deployment, move traffic to it from the application or a gateway, keep the previous deployment until the new one is validated, then delete the old one. Cancelling or finishing a training job never deletes deployments or stops their charges.

> **Exam trap.** Hosting a fine-tuned model costs per hour **while deployed**, even with no traffic. "Evaluate cheaply for a day" → Developer deployment. "Production, data must stay in the region" → Standard. "Stop paying for an old version" → delete its deployment.

<!-- section: key-points -->
## Key points

- Fine-tuning changes weights; it doesn't replace RAG for current data nor safety controls; compare with the baseline.
- SFT = demonstrations, DPO = preferred and rejected pairs, RFT = grader (`string_check`, `text_similarity`, `score_model`, `python`, `multi`).
- Training types: Standard (residency), Data zone (US), Global (cheaper, no residency), Developer (preemptible, cheapest).
- Foundry User trains, Foundry Owner deploys; DPO after SFT uses the fine-tuned model identifier.
- Synthetic data (preview): Simple Q&A or Tool use, one file under 20 MB, 50 to 1,000 samples, optional 80/20 split, JSONL output; review and mix with real data.
- Overfitting = training loss down, validation loss up: earlier checkpoint, fewer epochs; beware reward hacking in RFT.
- SFT bills tokens x epochs; RFT bills hours plus grader tokens, with a spending limit that pauses the job.
- Developer deployment: 24 hours, no hosting fee; production deployments bill hosting per hour until deleted.
