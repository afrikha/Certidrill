A SQL database project keeps the schema as code: one `.sql` file per object, built into a `.dacpac` that describes the desired state, then deployed by SqlPackage, which computes the `ALTER` statements a target needs. Exam questions give a pipeline excerpt, a project file or a requirement (block data loss, keep lookup data in Git, nobody deploys to production without approval, no secrets in the repository) and ask for the missing step, property or control.

<!-- section: sdk-projects | objectives: 2.3.3 -->
## Creating, building and validating SQL Database Projects

| | SDK-style project | Original project |
| --- | --- | --- |
| Project file | `<Sdk Name="Microsoft.Build.Sql" Version="..." />` | `<Import>` of SSDT build targets |
| Build | `dotnet build`, .NET 8 and later, Windows, Linux, macOS | MSBuild (.NET Framework) in Visual Studio |
| `.sql` files | Included by default (`**/*.sql`) | Each listed with `<Build Include>` |
| Tools | SQL Database Projects extension for VS Code, Database DevOps in SSMS, command line; Visual Studio 2022 SDK-style (preview) | SSDT in Visual Studio |

```bash
dotnet new install Microsoft.Build.Sql.Templates
dotnet new sqlproj -n SalesDb
dotnet build SalesDb/SalesDb.sqlproj          # produces bin/Debug/SalesDb.dacpac
dotnet build SalesDb/SalesDb.sqlproj /p:DSP=Microsoft.Data.Tools.Schema.Sql.Sql160DatabaseSchemaProvider
```

```text
<Project DefaultTargets="Build">
  <Sdk Name="Microsoft.Build.Sql" Version="2.1.0" />
  <PropertyGroup>
    <Name>SalesDb</Name>
    <DSP>Microsoft.Data.Tools.Schema.Sql.SqlAzureV12DatabaseSchemaProvider</DSP>
    <RunSqlCodeAnalysis>True</RunSqlCodeAnalysis>
  </PropertyGroup>
  <ItemGroup>
    <PostDeploy Include="Scripts\PostDeployment\PostDeploy.sql" />
  </ItemGroup>
</Project>
```

The **target platform** (`DSP`) decides which syntax is valid:

| Target | `DSP` value suffix |
| --- | --- |
| SQL Server 2022 / 2025 | `Sql160DatabaseSchemaProvider` / `Sql170DatabaseSchemaProvider` |
| Azure SQL Database | `SqlAzureV12DatabaseSchemaProvider` |
| SQL database in Fabric (preview) | `SqlDbFabricDatabaseSchemaProvider` |
| Fabric Data Warehouse | `SqlDwUnifiedDatabaseSchemaProvider` |

The build **validates** the model: T-SQL syntax for the target platform, and every reference (a view on a dropped column, a procedure that calls a missing table) is a build error. Warnings don't fail the build; code analysis rules flag design issues. A project targeting SQL Server 2017 fails to build when it uses a SQL Server 2025 function. Publishing to a different platform than the `DSP` fails unless `/p:AllowIncompatiblePlatform=true`.

> **Exam trap.** The `.dacpac` is a build output, not source: it is regenerated by every build. Validation of a merged change is `dotnet build`, which catches broken references that a clean Git merge doesn't.

<!-- section: source-control | objectives: 2.3.4 -->
## Configuring source control

Initialize Git at the project (or solution) root and organize files by schema and object type, one object per file: a change to a table touches only its file.

```text
SalesDb/
├── SalesDb.sqlproj
├── Tables/
│   ├── Customer.sql
│   └── OrderStatus.sql
├── Views/
├── StoredProcedures/
└── Scripts/
    ├── PreDeployment/PreDeploy.sql
    └── PostDeployment/
        ├── PostDeploy.sql
        └── OrderStatus.data.sql
```

```text
# .gitignore
bin/
obj/
*.dacpac
*.user
```

Commit the `.sqlproj`, every object script, the pre- and post-deployment scripts, schema compare settings (`.scmp`), the refactor log (`.refactorlog`) that records renames, and publish profiles **without** credentials.

<!-- section: reference-data | objectives: 2.3.2 -->
## Reference and static data in source control

Lookup data (statuses, countries, settings) belongs with the schema, in the **post-deployment script**, which runs after the schema changes on every deployment. A project has at most **one** pre-deployment and **one** post-deployment script; split the content with SQLCMD `:r` includes.

```text
-- Scripts/PostDeployment/PostDeploy.sql
:r .\OrderStatus.data.sql
:r .\Country.data.sql
```

```text
-- Scripts/PostDeployment/OrderStatus.data.sql : idempotent, safe on every deployment
MERGE INTO dbo.OrderStatus AS target
USING (VALUES (1, N'Pending'), (2, N'Shipped'), (3, N'Delivered'), (4, N'Cancelled'))
      AS source (StatusID, StatusName)
ON target.StatusID = source.StatusID
WHEN MATCHED AND target.StatusName <> source.StatusName THEN
    UPDATE SET StatusName = source.StatusName
WHEN NOT MATCHED BY TARGET THEN
    INSERT (StatusID, StatusName) VALUES (source.StatusID, source.StatusName)
WHEN NOT MATCHED BY SOURCE THEN
    DELETE;
```

Included files must be excluded from the model build, or the build tries to compile them as objects:

```text
<ItemGroup>
  <Build Remove="Scripts\PostDeployment\OrderStatus.data.sql" />
  <None Include="Scripts\PostDeployment\OrderStatus.data.sql" />
</ItemGroup>
```

Environment-specific values come from **SQLCMD variables** declared in the project (`$(Environment)`) and set at deployment (`/v:Environment=prod`). A `DefaultValue` declared in the project isn't compiled into the `.dacpac`: it only pre-fills the publish dialog of graphical tools, and a command-line deployment without `/v` or a publish profile gets empty values. The pre-deployment script prepares changes the model can't express, such as moving data before a column is dropped.

> **Exam trap.** A plain `INSERT` in the post-deployment script fails with a duplicate key on the second deployment. Reference data scripts must be idempotent: `MERGE`, or `IF NOT EXISTS` tests. Keep `WHEN NOT MATCHED BY SOURCE THEN DELETE` only if rows removed from Git must disappear from the database.

<!-- section: branching-prs | objectives: 2.3.5 -->
## Branching, pull requests and conflict resolution

- One short-lived **feature branch** per change (`git checkout -b feature/add-customer-email`), merged into `main` through a **pull request**; `main` stays deployable.
- The pull request runs a **CI build** (`dotnet build`, code analysis, unit tests) as a required check: Azure DevOps **Build Validation** branch policy, or a GitHub workflow on `pull_request` to `main` set as a required status check.
- Reviewers check broken dependencies, naming, data loss and whether reference data scripts need updating.

**Conflicts.** Two branches that edit the same `CREATE TABLE` (one adds `Phone`, the other `Address`) conflict in `Tables/Customer.sql`. Pull `main` into the feature branch, keep both columns in one valid statement, commit, then **build**: a text merge can still leave a procedure that references a column renamed in the other branch. Renames should be done through the project's refactoring so they go to the `.refactorlog`; otherwise the deployment sees a dropped column plus a new one, which loses the data (or is stopped by `BlockOnPossibleDataLoss`).

```bash
git checkout feature/add-customer-phone
git pull origin main
# edit Tables/Customer.sql to keep both columns
git add Tables/Customer.sql
git commit -m "Resolve conflict: keep Phone and Address"
dotnet build SalesDb.sqlproj
```

<!-- section: testing-strategy | objectives: 2.3.1 -->
## Testing strategy: unit and integration tests

| Level | What it proves | Where it runs |
| --- | --- | --- |
| Build validation | Syntax and object references are valid for the target | Every commit and pull request, no database needed |
| Unit tests | One procedure or function returns the right result for given inputs, raises the expected error for bad input | Against a test database deployed from the project |
| Integration tests | Multi-step scenarios: procedure sequences, triggers, views after related changes, application plus database | Against a dedicated, fully deployed test environment |

SQL Server unit tests (SSDT) have **pre-test** (arrange data), **test** (execute) and **post-test** (clean up) scripts, and **test conditions**: Row Count, Scalar Value, Expected Schema, Data Checksum, Empty ResultSet, Not Empty ResultSet, Execution Time, and **Inconclusive**, the default condition added to every new test: it always returns Inconclusive, verifies nothing and should be deleted once real conditions are added. A negative test expects an error (`ExpectedSqlException` with a severity and state) and fails if the procedure succeeds. The option **Automatically deploy the database project before unit tests are run** keeps the test database in sync.

```yaml
# GitHub Actions: after build and deployment to the test database
- name: Run database tests
  run: dotnet test ./SalesDb.Tests/SalesDb.Tests.csproj
```

Rules: never test against production; reset the database to a known state before each run; keep connection strings in configuration so local and CI runs target the right database; a failing test stops the pipeline before staging.

> **Exam tip.** "Catch a broken reference before merge" = build validation in the pull request. "Verify the discount procedure's result" = unit test. "Verify that placing an order updates stock, invoice and audit tables together" = integration test.

<!-- section: secrets-management | objectives: 2.3.6 -->
## Secrets management

| Secret | Where it goes |
| --- | --- |
| Azure sign-in for a GitHub workflow | **OpenID Connect** (federated credential on a Microsoft Entra app or user-assigned managed identity): `azure/login` with client, tenant and subscription IDs; no client secret; the job needs `permissions: id-token: write` |
| Values the workflow needs | Repository or **environment secrets** (`${{ secrets.NAME }}`); environment secrets are released only to jobs that target that environment |
| Azure DevOps credentials | **Service connection** with workload identity federation; variable groups **linked to Azure Key Vault**, or the Azure Key Vault task, secret variables |
| Database authentication | Microsoft Entra identity of the pipeline (`Authentication=Active Directory Default` or a service principal), not a SQL password |
| Environment-specific values in scripts | SQLCMD variables set by the pipeline from secrets |

Never commit connection strings or passwords (in `.sqlproj`, `.publish.xml`, workflow files or post-deployment scripts); rotate any remaining credential.

> **Exam trap.** A secret in a GitHub variable or in `env:` written in the workflow file is visible in the repository. "No credential stored anywhere" = OIDC federation, and the login step fails without `id-token: write`.

<!-- section: schema-drift | objectives: 2.3.7 -->
## Detecting schema drift

**Drift** is a difference between the deployed database and the project, usually a hotfix made directly in production.

| Tool | Use |
| --- | --- |
| Schema compare (VS Code, SSMS, Visual Studio) | Database versus project: shows drift and lets you pull selected changes into the project. Project versus database: previews a deployment. Options (ignore whitespace, column order) are saved in an `.scmp` file |
| `SqlPackage /Action:Extract` with `/p:ExtractTarget=SchemaObjectType` into the project folder | Scriptable: `git status` then lists every object that drifted |
| `SqlPackage /Action:DeployReport` | XML list of the operations a publish would run, including unexpected `Drop` or `TableDataMotion` |
| `SqlPackage /Action:DriftReport` | Changes made to a database **registered** as a data-tier application since its registration |

```bash
sqlpackage /Action:Extract /SourceConnectionString:"$PROD_CONN" \
  /TargetFile:SalesDb /p:ExtractTarget=SchemaObjectType
git status --porcelain          # one line per drifted object file
```

Resolve drift in one direction: a change worth keeping (a hotfix index) goes into the project through a pull request; an unauthorized change is overwritten by the next deployment of the project. Schedule the drift check in a pipeline and alert on changes.

<!-- section: update-deploy | objectives: 2.3.8 -->
## Updating a project and deploying changes

The cycle: change the object scripts in a branch, build, preview, merge, then publish the **same** `.dacpac` to each environment in turn.

```bash
sqlpackage /Action:Script /SourceFile:bin/Debug/SalesDb.dacpac \
  /TargetConnectionString:"$TEST_CONN" /OutputPath:deploy.sql
sqlpackage /Action:Publish /SourceFile:bin/Debug/SalesDb.dacpac \
  /TargetConnectionString:"$PROD_CONN" \
  /p:BlockOnPossibleDataLoss=true /p:DropObjectsNotInSource=false /v:Environment=prod
```

| Publish property | Default | Effect |
| --- | --- | --- |
| `BlockOnPossibleDataLoss` | True | Stops the deployment if a change (dropping a column, narrowing a type) could lose data |
| `DropObjectsNotInSource` | False | When true, drops target objects that aren't in the project |
| `AllowIncompatiblePlatform` | False | When true, allows a target platform different from `DSP` |

Publishing is incremental and idempotent: a new database is created in dependency order, an existing one gets only the needed changes, and publishing the same `.dacpac` twice changes nothing.

```yaml
name: sql-deploy
on:
  push:
    branches: [main]
permissions:
  id-token: write
  contents: read
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: dotnet build ./SalesDb/SalesDb.sqlproj -o ./out
      - uses: actions/upload-artifact@v4
        with: { name: dacpac, path: ./out/SalesDb.dacpac }
  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/download-artifact@v4
        with: { name: dacpac }
      - uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
      - uses: azure/sql-action@v2.3
        with:
          connection-string: ${{ secrets.AZURE_SQL_CONNECTION_STRING }}
          path: ./SalesDb.dacpac
          action: publish
```

`azure/sql-action` adds a temporary firewall rule for the runner's IP and removes it after the deployment. In Azure Pipelines, the equivalent is the `SqlAzureDacpacDeployment@1` task, or `sqlpackage` run as a script on any agent.

> **Exam trap.** Building a new `.dacpac` per environment breaks "what was tested is what is deployed". Build once, publish the same artifact everywhere, and run `Script` or `DeployReport` before production to review the generated `ALTER` statements.

<!-- section: pipeline-controls | objectives: 2.3.9 -->
## Controls for deployment pipelines

| Control | Azure DevOps | GitHub |
| --- | --- | --- |
| Protect `main` | Branch policies: minimum number of reviewers, linked work items, comment resolution, **Build Validation** | Branch protection rules or rulesets: required pull request reviews, required status checks |
| Mandatory reviewers for database files | Automatically included reviewers on a path such as `/Database/*` | `CODEOWNERS` with required review from code owners |
| When pipelines run (triggers) | `trigger` (CI on push); pull requests in Azure Repos Git: **Build Validation** branch policy only, because a PR trigger can't be configured in the YAML file (`pr` applies to GitHub and Bitbucket Cloud repositories) | `on: push`, `on: pull_request` |
| Approval before production | **Environment** with approvals and checks (approvers, business hours, branch control) | **Environment** protection rules: required reviewers, wait timer, deployment branches (only `main`) |
| Who can use production credentials | Service connection security and a **branch control** check limited to `main` | Environment secrets, released only after the environment's rules pass |

```text
# .github/CODEOWNERS : later rules win
*.sql            @contoso/db-team
/Database/       @contoso/db-team @contoso/dba-lead
```

```yaml
# Azure Pipelines: the deployment job waits for the production environment's approvals
stages:
  - stage: Build
    jobs:
      - job: Build
        steps:
          - task: DotNetCoreCLI@2
            inputs:
              command: build
              projects: SalesDb/SalesDb.sqlproj
              arguments: -o $(Build.ArtifactStagingDirectory)
          - publish: $(Build.ArtifactStagingDirectory)
            artifact: dacpac
  - stage: Deploy
    dependsOn: Build
    condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
    jobs:
      - deployment: DeployProduction
        environment: production
        strategy:
          runOnce:
            deploy:
              steps:
                - task: SqlAzureDacpacDeployment@1
                  inputs:
                    azureSubscription: sc-sql-prod
                    AuthenticationType: servicePrincipal
                    ServerName: sql-contoso.database.windows.net
                    DatabaseName: SalesDb
                    DeploymentAction: Publish
                    DacpacFile: $(Pipeline.Workspace)/dacpac/SalesDb.dacpac
```

Approvals and checks are configured on the **environment** (or the service connection), not in the YAML: a pipeline author can't remove them by editing the file.

> **Exam trap.** A `condition` on the branch in YAML isn't a control, because anyone who edits the pipeline can change it. "Only reviewed code from `main` can reach production, with a DBA approval" = branch policy or protection on `main`, plus environment approvals and a branch restriction on the production environment or service connection.

<!-- section: key-points -->
## Key points

- SDK-style project = `Microsoft.Build.Sql`, `dotnet build` on any OS, `.sql` files globbed; `DSP` sets the target platform; the build validates syntax and references.
- Commit object scripts, `.sqlproj`, pre/post-deployment scripts, `.refactorlog`, `.scmp`; ignore `bin/`, `obj/`, `*.dacpac`.
- Reference data = idempotent `MERGE` in the single post-deployment script, split with `:r`, included files removed from the build.
- Feature branches, pull requests with build validation, rebuild after resolving conflicts, renames through the refactor log.
- Build validation, unit tests, integration tests: in that order, never against production.
- OIDC federation (`id-token: write`), environment secrets, Key Vault-linked variable groups; no passwords in the repository.
- Drift: schema compare, Extract plus `git status`, `DeployReport`, `DriftReport` for registered databases.
- Publish one artifact everywhere; `BlockOnPossibleDataLoss` true by default; branch policies, code owners and environment approvals guard production.
