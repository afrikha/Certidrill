Every Google Cloud environment starts with the same steps: an organization resource at the root, folders and projects under it, organization policies that restrict what may be created, identities that come from Cloud Identity or an external identity provider, IAM roles granted on the right node, and the APIs each project needs. Associate Cloud Engineer questions on this chapter ask for the concrete action: the command, the role, the constraint or the console page.

<!-- section: resource-hierarchy | objectives: 1.1.1 -->
## Creating a resource hierarchy

```text
Organization (example.com)                organizations/123456789012
├── Folder: Production                    folders/111111111111
│   ├── Folder: Payments
│   │   └── Project: payments-prod-4821   projects/payments-prod-4821
│   └── Project: web-prod-1934
└── Folder: Non-production
    └── Project: web-dev-7720
```

| Node | What to know |
| --- | --- |
| Organization | Root node. A Google Workspace or Cloud Identity account maps to exactly one organization resource. Its initial policy grants **Project Creator** and **Billing Account Creator** to every user of the domain: remove these grants if only a platform team may create projects |
| Folder | Optional; requires an organization. Nests up to **10 levels**; at most **300 direct child folders** per parent. Display name 3 to 30 characters, unique among siblings. Must be empty before deletion |
| Project | Container of resources, APIs, billing link and quotas. A resource has exactly one parent |

A project has three identifiers:

| Identifier | Rules |
| --- | --- |
| Project ID | 6 to 30 characters, lowercase letters, digits and hyphens, starts with a letter, can't end with a hyphen. Globally unique, **can't be changed** after creation and can never be reused, even after deletion |
| Project number | Generated by Google, read-only |
| Project name | 4 to 30 characters, not unique, editable at any time |

```bash
# Folders: Folder Creator (or Folder Admin) on the parent
gcloud resource-manager folders create --display-name="Production" --organization=123456789012
gcloud resource-manager folders create --display-name="Payments" --folder=111111111111

# Projects: Project Creator (roles/resourcemanager.projectCreator) on the parent
gcloud projects create payments-prod-4821 --name="Payments prod" --folder=222222222222

# Move a project: Project Mover on the source and the destination (beta command)
gcloud beta projects move web-dev-7720 --folder=333333333333

# Shut down, then restore within 30 days
gcloud projects delete web-dev-7720
gcloud projects undelete web-dev-7720
```

Deleting a project shuts it down: billing and resource usage stop (charges can still accrue until the end of the current billing cycle, so disable billing first if needed), the project enters `DELETE_REQUESTED`, and after **30 days** it and all its data are permanently deleted. Some services, such as Cloud Storage and Pub/Sub, may delete data sooner. Until then the project still counts against your project quota. Restoring needs `resourcemanager.projects.undelete` on the project, and a restored project must be relinked to its billing account manually. Use project **liens** to protect important projects from accidental deletion.

When a project moves, roles granted directly on it move with it; roles and organization policies inherited from the old parent are replaced by those of the new parent.

> **Exam trap.** The project ID is the permanent, globally unique name used in commands and APIs; the project name is only a display label. "Rename the project ID" is never possible: create a new project and migrate.

## Setting up standalone organizations

There are two ways to get an organization resource:

| | Organization linked to Workspace or Cloud Identity | Standalone organization |
| --- | --- | --- |
| Prerequisite | A Workspace or Cloud Identity account with a verified DNS domain | None: no Cloud Identity and no custom domain |
| Creation | Automatic when a user of the account first signs in to the console and accepts the terms, or creates a project or billing account | Automatic when a new Free Trial customer signs up with a Google Account; not available to existing Google Cloud accounts |
| First administrator | The Cloud Identity or Workspace **super administrator**, who receives Organization Administrator | The signing-up user, who receives **Organization Owner** (`roles/cloudowner.admin`, managed outside IAM) and Organization Administrator |
| Name | From the primary domain | Default username plus `-org`, editable at any time |

In a standalone organization, Organization Owners are Google Accounts or workforce pool principals (never service accounts), and at least one active Google Account owner must remain. Add owners from the **Organization details** page; an invitation expires after 30 days. Having several owners avoids a single point of failure when an employee leaves.

A Cloud Identity super administrator with a verified domain can find the standalone organizations created by users of that domain (**Organizations > Admin Governance**) and **claim** them: claiming replaces the owners with the super administrator, and the former owners keep Organization Administrator. Claiming can't be undone.

**Organization Administrator** (`roles/resourcemanager.organizationAdmin`) manages allow and deny policies and views the hierarchy, but, by least privilege, it doesn't include creating folders or projects. Don't use super administrator accounts for daily work; delegate Organization Administrator to a group.

```bash
gcloud organizations list
gcloud organizations add-iam-policy-binding 123456789012 \
  --member="group:gcp-org-admins@example.com" \
  --role="roles/resourcemanager.organizationAdmin"
```

## Applying organization policies

IAM decides **who** may act; organization policies decide **what configurations** are allowed, whoever acts. A policy applies a **constraint** to an organization, folder or project and is inherited by every descendant.

| Constraint kind | Behavior |
| --- | --- |
| Managed (`constraints/compute.managed.*`, `iam.managed.*`…) | Google-managed replacements of legacy constraints, enforced or parameterized; not merged: a child enforces the parent's setting or overrides it |
| Legacy managed, list | Allowed or denied values (`in:eu-locations`, `under:folders/123`); values not allowed are denied. A child can merge with its parent (`inheritFromParent: true`) |
| Legacy managed, boolean | Enforced or not |
| Custom | Your own CEL condition on a resource type, `ALLOW` or `DENY`, defined at organization level |

Constraints the exam uses:

| Requirement | Constraint |
| --- | --- |
| Resources only in EU locations | `constraints/gcp.resourceLocations` (list) |
| Only identities of our domain in IAM policies | `constraints/iam.allowedPolicyMemberDomains` (list; managed: `iam.managed.allowedPolicyMembers`) |
| No external IPs on VMs | `constraints/compute.vmExternalIpAccess` (list; managed: `compute.managed.vmExternalIpAccess`) |
| No service account keys | `constraints/iam.disableServiceAccountKeyCreation` (managed: `iam.managed.disableServiceAccountKeyCreation`) |
| No default network in new projects | `constraints/compute.skipDefaultNetworkCreation` |
| OS Login required | `constraints/compute.requireOsLogin` |
| No object ACLs / no public buckets | `constraints/storage.uniformBucketLevelAccess`, `constraints/storage.publicAccessPrevention` |
| Only approved services can be used at runtime | `constraints/gcp.restrictServiceUsage` |

```yaml
# policy.yaml: allow only EU locations for the Production folder
name: folders/111111111111/policies/gcp.resourceLocations
spec:
  rules:
  - values:
      allowedValues:
      - in:eu-locations
```

```bash
gcloud org-policies set-policy policy.yaml
gcloud org-policies describe gcp.resourceLocations --effective --project=payments-prod-4821
gcloud org-policies reset compute.vmExternalIpAccess --project=web-dev-7720
gcloud org-policies delete compute.vmExternalIpAccess --project=web-dev-7720
gcloud org-policies set-custom-constraint constraint.yaml
```

- Setting policies requires **Organization Policy Administrator** (`roles/orgpolicy.policyAdmin`) on the organization.
- `describe --effective` shows the result of inheritance; without it you see only the policy set on that node.
- Policies are **not retroactive**: existing non-compliant resources keep running and are reported as violations.
- Test first: a policy with a `dryRunSpec` (applied with `--update-mask=dryRunSpec`) logs violations in audit logs without blocking; **Policy Simulator** lists resources that would violate a new policy.
- Rules can be conditional on **tags** (enforce only on resources tagged `environment=production`).
- Organizations created on or after **May 3, 2024** get a **security baseline** enforced automatically, including `iam.managed.disableServiceAccountKeyCreation`, `iam.automaticIamGrantsForDefaultServiceAccounts`, `iam.allowedPolicyMemberDomains` and `storage.uniformBucketLevelAccess`.

> **Exam trap.** A role that allows an action doesn't override an organization policy. If a project Admin can't create a VM with an external IP or a bucket in `us-central1`, the fix is the policy (or an exception set on that project by a policy administrator), not another IAM role.

## Granting IAM roles in a project

An allow policy binds **principals** to **roles** on a resource. Principal formats: `user:ana@example.com`, `group:devs@example.com`, `serviceAccount:app@my-proj.iam.gserviceaccount.com`, `domain:example.com`, and workforce principals (`principal://…`, `principalSet://…`).

| Role type | Examples | Use |
| --- | --- | --- |
| Basic | Admin (`roles/admin`), Writer (`roles/writer`), Reader (`roles/reader`); legacy Owner, Editor, Viewer (`roles/owner`, `roles/editor`, `roles/viewer`) | Very broad; avoid in production. Legacy basic roles don't accept IAM Conditions; prefer Admin, Writer, Reader when a basic role is unavoidable. Project creators receive Owner |
| Predefined | `roles/compute.instanceAdmin.v1`, `roles/storage.objectViewer` | Default choice, maintained by Google |
| Custom | Your permission list | Created at organization or project level only, never on a folder |

```bash
gcloud projects add-iam-policy-binding web-prod-1934 \
  --member="group:web-ops@example.com" --role="roles/compute.instanceAdmin.v1"

gcloud projects add-iam-policy-binding web-prod-1934 \
  --member="user:auditor@example.com" --role="roles/reader" --condition=None

gcloud projects remove-iam-policy-binding web-prod-1934 \
  --member="user:ana@example.com" --role="roles/editor"

gcloud projects get-iam-policy web-prod-1934 --format=json > policy.json
```

- Granting roles on a project requires **Project IAM Admin** (`roles/resourcemanager.projectIamAdmin`) or a role that includes `resourcemanager.projects.setIamPolicy`.
- Grant to **groups**, then manage membership in Cloud Identity.
- With `get-iam-policy`/`set-iam-policy` (read-modify-write), keep the `etag`: it prevents overwriting a concurrent change.
- Changes usually apply within 2 minutes, sometimes 7 minutes or more.
- Granting Owner to a user outside the organization requires the console.

> **Exam trap.** Removing a role on the project changes nothing if the user inherits it from a folder or the organization: allow policies only add. Remove the binding where it was granted (or use a deny policy).

## Managing users and groups in Cloud Identity

Google Cloud has no user directory of its own: users and groups live in **Cloud Identity** or **Google Workspace**, managed in the Google Admin console. Cloud Identity Free covers users, groups, GCDS and SSO with an external IdP; Premium adds automated provisioning from SaaS applications, advanced device management and Context-Aware Access.

| Need | Tool |
| --- | --- |
| Create a few users or groups by hand | Admin console (Directory > Users, Groups) |
| Create groups or add members from scripts | `gcloud identity groups create`, `gcloud identity groups memberships add`, or the Cloud Identity / Directory APIs |
| Keep users and groups in sync with on-premises Active Directory or LDAP | **Google Cloud Directory Sync** (GCDS): free tool that runs in your environment, one-way sync (AD to Google), scheduled; passwords are not synced |
| Keep users and groups in sync with Microsoft Entra ID | The Entra ID gallery app "Google Cloud/G Suite Connector by Microsoft" (automatic provisioning), plus SAML SSO |
| Let users sign in with their corporate password | SSO: Cloud Identity delegates authentication to the IdP (AD FS, Entra ID, Okta) over SAML |

```bash
gcloud identity groups create gcp-web-ops@example.com \
  --organization="example.com" --display-name="Web operations"

gcloud identity groups memberships add \
  --group-email="gcp-web-ops@example.com" --member-email="ana@example.com"
```

Provisioning (creating and deleting accounts) and authentication (checking the password) are separate: SSO alone doesn't create users, and a user must be provisioned before signing in.

> **Exam tip.** "Users are managed in Active Directory; disabling an employee there must remove their Google Cloud access" points to GCDS for provisioning plus SAML SSO. "No synchronization at all" points to Workforce Identity Federation.

## Configuring Workforce Identity Federation

Workforce Identity Federation lets employees, partners and contractors use an external IdP (OIDC or SAML 2.0) to access Google Cloud **without** creating Cloud Identity accounts: it is sync-less. Don't confuse it with **Workload** Identity Federation, which is for applications.

1. Have an organization, Essential Contacts, and **Workforce Identity Pool Admin** (`roles/iam.workforcePoolAdmin`) on the organization.
2. Create a **workforce pool** at organization level (`--location=global`); session duration 15 minutes to 12 hours, default 1 hour.
3. Create a **provider** (OIDC or SAML) with an **attribute mapping**: `google.subject` is required (stable value, at most 127 bytes), `google.groups` and `google.display_name` optional; add an **attribute condition** to accept only some identities.
4. Grant IAM roles to pool principals.
5. Users sign in through the console (federated) or the gcloud CLI.

```bash
gcloud iam workforce-pools create contractors-pool \
  --organization=123456789012 --location=global \
  --display-name="Contractors" --session-duration=3600s

gcloud iam workforce-pools providers create-oidc entra-oidc \
  --workforce-pool=contractors-pool --location=global \
  --issuer-uri="ISSUER_URI" --client-id="CLIENT_ID" \
  --web-sso-response-type="id-token" \
  --web-sso-assertion-claims-behavior="only-id-token-claims" \
  --attribute-mapping="google.subject=assertion.sub,google.groups=assertion.groups"

gcloud projects add-iam-policy-binding web-dev-7720 --role="roles/reader" \
  --member="principalSet://iam.googleapis.com/locations/global/workforcePools/contractors-pool/group/dev-contractors"

gcloud iam workforce-pools create-login-config contractors-pool/entra-oidc \
  --output-file=login-config.json
gcloud auth login --login-config=login-config.json
```

| Principal | Identifier |
| --- | --- |
| One user | `principal://iam.googleapis.com/locations/global/workforcePools/POOL_ID/subject/SUBJECT` |
| A group | `principalSet://iam.googleapis.com/locations/global/workforcePools/POOL_ID/group/GROUP_ID` |
| An attribute value | `principalSet://…/workforcePools/POOL_ID/attribute.ATTRIBUTE_NAME/VALUE` |
| The whole pool | `principalSet://…/workforcePools/POOL_ID/*` |

Deleted pools and providers can be undeleted within 30 days.

## Enabling APIs in projects

A product can't be used in a project until its API (service) is enabled there; the first call to a disabled API fails with an error telling you to enable it. The Service Usage API is enabled by default; check the others with `gcloud services list --enabled`.

```bash
gcloud services list --available --filter="name:compute"
gcloud services enable compute.googleapis.com container.googleapis.com --project=web-prod-1934
gcloud services list --enabled --project=web-prod-1934
gcloud services disable container.googleapis.com --project=web-dev-7720
```

- Role: **Service Usage Admin** (`roles/serviceusage.serviceUsageAdmin`) enables and disables services; Service Usage Consumer only uses them.
- `--project` targets a project for one command; `gcloud config set project PROJECT_ID` changes the default for all later commands.
- Disabling fails if enabled services depend on the API; `--force` also disables the dependents. Disabling doesn't delete data: storage keeps being billed.
- The REST `services.batchEnable` method enables up to 20 services per call.
- To restrict which services can be used across projects, use the `gcp.restrictServiceUsage` constraint (allowlist or denylist). It controls runtime access to the resources of in-scope services (services whose resources are direct children of a project, folder or organization, such as Compute Engine and Cloud Storage), also restricts dependent services (GKE when Compute Engine is denied), and excludes essential dependencies such as IAM, Cloud Logging and Cloud Monitoring.

> **Exam trap.** "The command fails with `SERVICE_DISABLED` / API has not been used in project" is fixed with `gcloud services enable`, not with an IAM role.

<!-- section: key-points -->
## Key points

- Organization, then folders (10 levels, 300 children per parent), then projects; policies are inherited downward.
- Project ID: 6 to 30 characters, globally unique, permanent; deletion is reversible for 30 days with `gcloud projects undelete`.
- Standalone organizations need no Cloud Identity or domain; Organization Owner is managed outside IAM; super administrators can claim them.
- Organization policies restrict configurations whatever the IAM roles; test with dry run and Policy Simulator; not retroactive.
- Basic roles are Admin, Writer, Reader (legacy Owner, Editor, Viewer); grant predefined roles to groups; a lower level can't remove an inherited role.
- GCDS syncs AD one way without passwords; Workforce Identity Federation needs no sync at all.
- Enable each API per project with `gcloud services enable`.
