Windows Server is administered remotely: from Windows Admin Center on-premises or in the Azure portal, from PowerShell over WinRM or SSH, through JEA endpoints, or with Remote Desktop. Exam questions give a constraint (no inbound port, no stored credentials, least privilege, a second server reached from the first) and ask which tool or configuration meets it.

## Windows Admin Center on-premises

Windows Admin Center (WAC) is a browser-based management tool. Its **gateway** runs on a Windows machine and manages the target servers with PowerShell remoting and WMI over **WinRM**: nothing is installed on the managed servers. The current gateway is the **modernized gateway** (.NET 8 backend, Kestrel web server, HTTP/2).

| Installation type | Installed on | Use |
| --- | --- | --- |
| Local client | Windows 11, opened at `https://localhost:6516` | Quick start, tests, small scale |
| Gateway server | Windows Server 2016 to 2025 | Shared access from any browser that reaches the gateway; large scale |
| Managed server | The server to manage itself | Possible but not recommended: manage it remotely instead |
| Failover cluster | A cluster, active-passive | High availability of the gateway service |

Rules to know:

- Installing WAC on a **domain controller** isn't supported.
- Managed nodes: Windows Server 2016 to 2025 and their failover clusters, Windows 11; Windows Server 2012 and 2012 R2 need WMF 5.1 or later.
- TLS certificate: an existing certificate with the Server Authentication EKU in `LocalMachine\My`, or a **self-signed** certificate generated by the installer, valid **60 days** (tests only).
- Setup: **Express** (network access and port chosen from the OS) or **Custom** (port, certificate thumbprint, endpoint FQDN, trusted hosts mode, WinRM over HTTPS).
- Supported browsers: Microsoft Edge and Google Chrome.

Access has two layers:

| Layer | Roles | Configured by |
| --- | --- | --- |
| Gateway access | **Gateway users** (connect and manage servers) and **Gateway administrators** (also decide who has access and how users authenticate) | Active Directory or local groups (optionally smart card groups), or Microsoft Entra ID (adds Conditional Access and MFA) |
| Target server | The user's own credentials must be administrator on each target, **or** a WAC role-based access control role | The server's **Role-based access control** page, or a script distributed with DSC to many servers |

The built-in RBAC roles are delivered as a **JEA endpoint** on each managed server: **Administrators** (most tools, but no PowerShell or Remote Desktop: jump-server scenario), **Readers** (view only), **Hyper-V Administrators** (change VMs and virtual switches, the rest read-only). Custom roles can't be created.

> **Exam trap.** Gateway access never grants rights on the target servers. A Gateway user without admin rights or a WAC RBAC role on Server2 can sign in to the gateway but can't manage Server2.

## Windows Admin Center in the Azure portal

WAC can also be opened from the Azure portal, on the resource page of an **Azure VM** or of an **Azure Arc-enabled server** (Settings > Windows Admin Center). It's installed as the `AdminCenter` VM extension (publisher `Microsoft.AdminCenter`), on **each** machine, at no cost.

| | Azure VM | Arc-enabled server |
| --- | --- | --- |
| Operating system | Windows Server 2016 or later (also Windows 10/11) | Windows Server 2016 or later |
| Memory | 3 GiB or more | 3 GB or more |
| Inbound connectivity | Private IP (recommended, from a network connected to the virtual network, such as a VPN) or public IP with an inbound NSG rule on the WAC port (default **6516**) from the management IPs | **None**: the portal reaches the machine through a reverse proxy session of the Connected Machine agent (`Microsoft.HybridConnectivity` resource provider) |
| Outbound | HTTPS 443 to the `WindowsAdminCenter` and `AzureActiveDirectory` service tags | HTTPS 443 to the WAC service endpoints |
| Role to install | Owner or Contributor | Owner, Contributor or Windows Admin Center Administrator Login |
| Role to connect | **Reader** + **Windows Admin Center Administrator Login** on the machine | **Reader** + **Windows Admin Center Administrator Login** on the machine |
| Clouds | Azure public cloud only | Azure public cloud only, in the supported regions |

```powershell
# Azure VM: install the extension on port 6516
Set-AzVMExtension -ResourceGroupName RG1 -Location westeurope -VMName VM1 `
    -Name "AdminCenter" -Publisher "Microsoft.AdminCenter" -Type "AdminCenter" `
    -TypeHandlerVersion "0.0" -Settings @{ "port" = "6516" }

# Arc-enabled server: allow the WAC port for incoming reverse proxy connections
azcmagent config set incomingconnections.ports 6516
```

> **Exam trap.** Owner or Contributor on the VM lets you install the extension but not sign in through WAC: connecting needs the **Windows Admin Center Administrator Login** role, which can't be assigned at management group scope.

Limitations: Azure Bastion and traffic redirected by Azure Firewall aren't supported; third-party WAC extensions aren't available; installing the extension on a machine that already runs a standalone WAC gateway limits it to managing itself.

## PowerShell remoting and the double hop

PowerShell remoting uses **WinRM** (WS-Management): TCP **5985** (HTTP, the traffic is still encrypted by Kerberos or NTLM) and **5986** (HTTPS, needs a certificate listener). It's enabled by default on Windows Server; `Enable-PSRemoting` re-creates the listener, firewall rules and default endpoints. Inside a domain, authentication is Kerberos; to a workgroup server or by IP address, add the target to `TrustedHosts` on the client (NTLM) or use HTTPS.

```powershell
Enter-PSSession -ComputerName SRV1                       # interactive, one server
Invoke-Command -ComputerName SRV1, SRV2 -ScriptBlock { Get-Service W32Time }   # fan-out
Set-Item WSMan:\localhost\Client\TrustedHosts -Value "WG-SRV1" -Concatenate
```

The **second hop** problem: from ServerA you open a session on ServerB, then a command on ServerB accesses ServerC (a share, another remote session). Kerberos doesn't forward your credentials by default, so the second hop fails with access denied.

| Option | Credentials stored on ServerB | Main points |
| --- | --- | --- |
| CredSSP | **Yes** (exposed if ServerB is compromised) | `Enable-WSManCredSSP -Role Client -DelegateComputer ServerB` on A, `-Role Server` on B. Doesn't work for members of Protected Users. Only in highly trusted cases |
| Kerberos unconstrained delegation | No | Not recommended: no control over where credentials go |
| Kerberos constrained delegation | No | Set on ServerB's AD object, needs Domain Admins rights, single domain |
| **Resource-based Kerberos constrained delegation** | No | Set on **ServerC** with `Set-ADComputer`, no Domain Admins needed, works across domains and forests, Windows Server 2012 or later |
| JEA endpoint on ServerB | No | The session runs as a virtual account or gMSA that has the needed access |
| Explicit credentials in the script (`$Using:cred`) | No | No server configuration, awkward code |

```powershell
# Resource-based constrained delegation: ServerB may delegate to ServerC
$ServerB = Get-ADComputer -Identity ServerB
Set-ADComputer -Identity ServerC -PrincipalsAllowedToDelegateToAccount $ServerB

# Clear ServerB's cached Kerberos tickets (the KDC caches failures for 15 minutes)
Invoke-Command -ComputerName ServerB -ScriptBlock { klist purge -li 0x3e7 }
```

> **Exam trap.** Resource-based constrained delegation is configured on the **resource** (ServerC, the last hop), listing the computer that delegates (ServerB). Classic constrained delegation is configured on ServerB. Both store no credentials, unlike CredSSP.

## Just Enough Administration (JEA)

JEA is a constrained PowerShell remoting endpoint: users connect with their own non-privileged accounts, see only the commands allowed for their role, and the commands run under a privileged **run-as** identity. Two files:

| File | Created with | Contains | Location |
| --- | --- | --- | --- |
| Role capability (`.psrc`) | `New-PSRoleCapabilityFile` | What a role may run: `VisibleCmdlets` (with allowed parameters and values), `VisibleFunctions`, `VisibleExternalCommands`, `VisibleProviders` | A `RoleCapabilities` folder inside a PowerShell module in `$env:PSModulePath` |
| Session configuration (`.pssc`) | `New-PSSessionConfigurationFile` | Who gets which role (`RoleDefinitions`), run-as identity, transcripts, language mode | Any folder; registered with `Register-PSSessionConfiguration` |

Run-as identity:

| Setting | Identity | Use |
| --- | --- | --- |
| `RunAsVirtualAccount = $true` | A temporary account per session, member of local **Administrators** (on a domain controller: **Domain Admins**) | Default choice, local tasks |
| `RunAsVirtualAccountGroups` | Virtual account placed only in the listed local groups | Fewer rights than local admin |
| `GroupManagedServiceAccount` | A gMSA, one domain identity shared by all users | The commands must reach **network resources** (shares, other servers) |

```powershell
New-PSSessionConfigurationFile -Path .\DnsOps.pssc -SessionType RestrictedRemoteServer `
    -RunAsVirtualAccount -TranscriptDirectory "C:\ProgramData\JEA\Transcripts" `
    -RoleDefinitions @{ 'CONTOSO\G-DnsOperators' = @{ RoleCapabilities = 'DnsOperator' } }
Test-PSSessionConfigurationFile -Path .\DnsOps.pssc
Register-PSSessionConfiguration -Name DnsOps -Path .\DnsOps.pssc

# From the operator's computer
Enter-PSSession -ComputerName DNS1 -ConfigurationName DnsOps
```

`RestrictedRemoteServer` sessions run in **NoLanguage** mode with a handful of default commands (`Get-Command`, `Get-Help`, `Exit-PSSession`, `Select-Object`, `Measure-Object`...). `RoleCapabilities` uses the `.psrc` file's base name. To change a configuration, unregister it and register the updated file. `RequiredGroups` adds conditions, such as membership in a smart card group.

> **Exam tip.** "Help desk operators must restart the DNS service on DNS1 without being administrators, and every command must be logged" means JEA with a role capability exposing `Restart-Service -Name DNS` and a transcript directory. A gMSA is needed only if the commands must access another server.

## Remote SSH access

Windows Server includes the OpenSSH server (`sshd` service). On **Windows Server 2025** it's **installed by default**, and **Remote SSH Access** can be enabled or disabled on the Local Server page of Server Manager. On Windows Server 2019 and 2022, add the OpenSSH Server optional feature first.

```powershell
# Windows Server 2019/2022: add the feature
Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0
Set-Service -Name sshd -StartupType Automatic
Start-Service sshd
# The setup creates the inbound firewall rule OpenSSH-Server-In-TCP (TCP 22)

# Connect from a client
ssh contoso\admin1@srv1.contoso.com
```

Configuration lives in `C:\ProgramData\ssh` (`sshd_config` and the host keys). Restart `sshd` after a change.

| Requirement | Configuration |
| --- | --- |
| Only some users may connect | Add them to the local **OpenSSH Users** group (Windows Server 2025), or `AllowGroups` / `AllowUsers` in `sshd_config` |
| Key authentication, standard user | Public key in `C:\Users\<user>\.ssh\authorized_keys` |
| Key authentication, **administrator** | Public key in `C:\ProgramData\ssh\administrators_authorized_keys`, ACL limited to Administrators and SYSTEM |
| Land in PowerShell instead of cmd.exe | `DefaultShell` value under `HKLM:\SOFTWARE\OpenSSH` |
| Load private keys on the client | `ssh-agent` service (disabled by default), then `ssh-add` |
| PowerShell remoting over SSH | PowerShell 7 on both sides, a `Subsystem powershell` line in `sshd_config`, then `Enter-PSSession -HostName` |

```powershell
icacls.exe "$env:ProgramData\ssh\administrators_authorized_keys" /inheritance:r /grant "Administrators:F" /grant "SYSTEM:F"
New-ItemProperty -Path "HKLM:\SOFTWARE\OpenSSH" -Name DefaultShell `
    -Value "C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe" -PropertyType String -Force
```

> **Exam trap.** For a member of Administrators, a key placed in the user's own `authorized_keys` is ignored: the default `sshd_config` sends administrators to `administrators_authorized_keys`. A wrong ACL on that file also makes key authentication fail.

## Remote desktop access

Remote Desktop (RDP, TCP and UDP **3389**) is disabled by default on Windows Server. Enable it in Server Manager (Local Server > Remote Desktop), in `sconfig`, or with PowerShell, and open the **Remote Desktop** firewall group.

```powershell
Set-ItemProperty -Path "HKLM:\System\CurrentControlSet\Control\Terminal Server" -Name fDenyTSConnections -Value 0
Enable-NetFirewallRule -DisplayGroup "Remote Desktop"
Add-LocalGroupMember -Group "Remote Desktop Users" -Member "CONTOSO\G-Operators"
```

| Point | Rule |
| --- | --- |
| Who can sign in | Administrators and members of **Remote Desktop Users** (both hold the user right *Allow log on through Remote Desktop Services*); a *Deny log on through Remote Desktop Services* right wins |
| Network Level Authentication (NLA) | Required by default: the user authenticates before a session is created, which protects the server from unauthenticated resource use |
| Licensing | Without the Remote Desktop Services role, two simultaneous administrative sessions are allowed; more users need RD Session Host and RDS CALs |
| Port | Change it in `PortNumber` under `HKLM\System\CurrentControlSet\Control\Terminal Server\WinStations\RDP-Tcp`, then update the firewall |
| Central configuration | GPO: Computer Configuration > Policies > Administrative Templates > Windows Components > Remote Desktop Services |

Protect administrator credentials on the target:

| Mode | Command | Behavior |
| --- | --- | --- |
| Restricted Admin mode | `mstsc /restrictedAdmin` | Credentials aren't sent to the server; the user must be in the target's **Administrators** group; network access from the session uses the **server's identity** (no single sign-on, no multi-hop RDP) |
| Remote Credential Guard | `mstsc /remoteGuard` | Credentials stay on the client; network access from the session works **as the user** (single sign-on, multi-hop RDP); **Kerberos only** (no NTLM fallback), target joined to AD DS; not through RD Gateway or RD Connection Broker |

Both modes need the policy *Remote host allows delegation of nonexportable credentials* enabled on the target. On the clients, the policy *Restrict delegation of credentials to remote servers* (Administrative Templates > System > Credentials Delegation) can require Restricted Admin, require Remote Credential Guard, or require either (Remote Credential Guard first).

> **Exam tip.** "Admins must reach file shares from the RDP session without their credentials being stored on the server" means Remote Credential Guard. Restricted Admin mode also avoids storing credentials, but the session accesses the network as the server, not as the user.

For Azure VMs, prefer no public RDP port: Azure Bastion or just-in-time VM access (chapter on Azure VMs).

<!-- section: key-points -->
## Key points

- WAC gateway: not on a domain controller; Gateway users vs Gateway administrators; target rights come from admin credentials or WAC RBAC roles (JEA).
- WAC in the Azure portal: `AdminCenter` extension; Azure VM needs a path to port 6516, Arc needs no inbound port; connect with Reader + Windows Admin Center Administrator Login.
- WinRM 5985/5986; second hop: prefer resource-based constrained delegation (set on the last server) or JEA; CredSSP stores credentials.
- JEA: `.psrc` (what) in a module's `RoleCapabilities` folder + `.pssc` (who, run as) registered as an endpoint; gMSA for network access.
- OpenSSH: installed by default on Windows Server 2025; administrators' keys in `administrators_authorized_keys`.
- RDP: off by default, NLA on, Remote Desktop Users group; Remote Credential Guard keeps credentials on the client and acts as the user.
