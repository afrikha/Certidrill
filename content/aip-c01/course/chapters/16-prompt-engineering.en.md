At professional level, prompt engineering is an engineering discipline: prompts are versioned assets with owners, tests and approval gates, and complex tasks are split into chains of prompts with branching and validation. This chapter covers instruction frameworks with Amazon Bedrock Prompt Management and Amazon Bedrock Guardrails, conversational context, prompt governance, quality assurance, iterative refinement techniques and multi-step prompt systems with Amazon Bedrock Flows (the exam guide calls them Prompt Flows).

## Instruction frameworks that control FM behavior

A robust instruction framework has three layers: a **role and rules** layer (system prompt), a **format** layer (templates and output schemas) and an **enforcement** layer that does not rely on the model obeying (guardrails, schema validation).

**Bedrock Prompt Management** stores reusable prompts:

| Element | Detail |
| --- | --- |
| Variables | `{{variable}}` placeholders filled at test or run time |
| Template type | `TEXT` or `CHAT`; `CHAT` requires a model that supports the Converse API, and prompt caching requires `CHAT` |
| System prompt | Role definition, scope and rules (models that support Converse or the Anthropic Messages API) |
| Inference configuration | `maxTokens`, `temperature`, `topP`, `stopSequences`; model-specific fields in `additionalModelRequestFields` |
| Tools | Tool configuration stored with the prompt, for models that support tool use |
| Variants | Up to 3 variants (different wording, model or settings) compared side by side |
| Metadata | Key-value pairs on each variant (owner, use case, ticket) |

The application then calls the prompt by ARN. With a Prompt Management ARN as `modelId`, the Converse request **cannot** include `system`, `inferenceConfig`, `toolConfig` or `additionalModelRequestFields`: they come from the managed prompt, which is how a central team enforces role definitions. The request supplies `promptVariables` and may append `messages`.

```bash
aws bedrock-runtime converse \
  --model-id arn:aws:bedrock:us-east-1:111122223333:prompt/PROMPT12345:3 \
  --prompt-variables '{"customer_tier": {"text": "gold"}, "question": {"text": "Can I change my delivery date?"}}'
```

**Bedrock Guardrails** enforce responsible AI rules on inputs and outputs, independently of the prompt and of the model:

| Policy | Purpose |
| --- | --- |
| Content filters | Hate, insults, sexual, violence, misconduct, with configurable strength; the prompt attack category detects jailbreaks and prompt injection on inputs |
| Denied topics | Topics the application must refuse (investment advice in a banking assistant) |
| Word filters | Exact words and phrases, profanity |
| Sensitive information filters | Block or mask PII and custom regex entities in inputs and responses |
| Contextual grounding checks | Block or flag responses not grounded in the source or not relevant to the query |
| Automated Reasoning checks | Validate responses against formal rules derived from policy documents |

Attach a guardrail in Converse with `guardrailConfig` (identifier and version), in `RetrieveAndGenerate` through `generationConfiguration`, or call `ApplyGuardrail` on any text, including output from models outside Bedrock.

**Response format templates**: state the format in the prompt (sections, length, JSON keys) and, when code consumes the output, enforce it with **structured outputs**: a JSON schema in `outputConfig.textFormat` (Converse) or `"strict": true` on a tool definition. Bedrock then constrains decoding to the schema. Every object in the schema must set `"additionalProperties": false`; the first request with a new schema can take up to about 90 seconds to compile (cached for 24 hours), so set client timeouts to at least 120 seconds.

> **Exam trap.** "Never discuss competitors" written in the system prompt is guidance, not a control: a prompt injection can override it. When the requirement says "must" or "guarantee", add a guardrail denied topic. When downstream code needs valid JSON every time, use structured outputs rather than "respond in JSON" in the prompt.

## Interactive systems that maintain context

Bedrock inference APIs are stateless: every Converse call must carry the conversation history the model needs. The application owns the state.

| Need | AWS design |
| --- | --- |
| Conversation history across turns and devices | DynamoDB table: partition key `session_id`, sort key turn timestamp, TTL attribute to expire old sessions; load the last turns into `messages` |
| History grows past the context window | Keep the last N turns plus a running summary generated by a cheaper model, stored in the same item |
| Agent memory with extraction of preferences and facts across sessions | AgentCore Memory: short-term events per session, long-term strategies (semantic, user preference, summary, episodic) |
| Detect what the user wants before choosing a prompt or a flow | Amazon Comprehend custom classification (real-time endpoint) trained on labeled utterances, or a small FM classification prompt |
| Language detection, entities, sentiment to adapt the reply | Amazon Comprehend built-in APIs |
| Ask a clarifying question when information is missing | Step Functions: a Choice state checks the extracted slots; if one is missing, a task sends the question and waits for the answer (task token or a new execution per turn) |

Clarification workflow:

```text
Receive message
  -> classify intent (Comprehend or FM)
  -> extract required fields (FM with structured output)
  -> Choice: all required fields present?
       no  -> generate clarifying question, store state in DynamoDB, return to user
       yes -> call business API, generate answer, append turn to DynamoDB
```

DynamoDB items are limited to 400 KB, so very long histories go to S3 with a pointer in the item, or are summarized.

> **Exam tip.** "The chatbot forgets what the user said two messages ago" is a missing history design (DynamoDB or AgentCore Memory), not a model problem. "Users ask vague questions and get generic answers" calls for intent detection plus a clarification step.

## Prompt management and governance

Treat prompts like code: parameterized templates, versions, reviews, approvals, audit.

**Versions**: saving a prompt updates its working **draft**. A **version** is an immutable snapshot of the draft, numbered from 1; the application calls a specific version ARN (`prompt/PROMPT12345:3`), so editing the draft never changes production. Rolling back means pointing the application (or its configuration in AWS AppConfig or Parameter Store) to the previous version ARN.

**Approval workflow**:

1. Authors edit the draft; prompt templates are also kept as files in an S3 repository (versioning enabled) or a Git repository, with metadata (owner, purpose, model).
2. A pipeline runs the prompt test suite against the draft.
3. A reviewer approves (CodePipeline manual approval action, or a Step Functions task token sent to the reviewer).
4. Only the pipeline role holds `bedrock:CreatePromptVersion` in production; authors have draft permissions only.
5. The new version ARN is published to the application configuration.

**Audit and monitoring**:

| Question | Source |
| --- | --- |
| Who created, changed or versioned a prompt? | AWS CloudTrail management events for the Bedrock Prompt Management API |
| Which prompts, inputs and outputs reached the model? | Bedrock model invocation logging to CloudWatch Logs or S3 |
| Which team, tenant or prompt version produced this invocation? | `requestMetadata` on Converse (up to 16 key-value pairs) to filter invocation logs |
| Who may read logs that contain prompts and responses? | CloudWatch Logs resource access through IAM, log group encryption with KMS |

> **Exam trap.** CloudTrail records API activity (who called `UpdatePrompt` or `InvokeModel`), not the prompt text sent to the model. To retain inputs and outputs, enable model invocation logging.

## Quality assurance for prompts

A prompt change can silently break a downstream parser or degrade accuracy. Build tests that run on every change and monitors that run in production.

| Check | Implementation |
| --- | --- |
| Output is valid JSON with the required keys | Lambda function validating against the JSON schema (or structured outputs at generation time) |
| Output respects business rules (no price above list price, cites a source) | Lambda validators with deterministic rules |
| Edge cases: empty input, very long input, other languages, injection attempts, missing fields | Step Functions test harness: a Map state runs every test case through the prompt version, Lambda scores each result, a final state computes the pass rate |
| Semantic quality (relevance, correctness, tone) | LLM-as-a-judge with Amazon Bedrock evaluations, or a judge prompt scored against a golden dataset |
| Regression after a prompt or model change | Compare the new version's scores with the current version on the same dataset; block the release below a threshold |
| Drift in production | Publish custom CloudWatch metrics (validation failures, refusal rate, average output tokens, user thumbs-down rate) and alarm on change |

```json
{
  "Type": "Map",
  "ItemsPath": "$.testCases",
  "MaxConcurrency": 10,
  "ItemProcessor": {
    "ProcessorConfig": { "Mode": "INLINE" },
    "StartAt": "RunPrompt",
    "States": {
      "RunPrompt": {
        "Type": "Task",
        "Resource": "arn:aws:states:::lambda:invoke",
        "Parameters": { "FunctionName": "run-prompt-version", "Payload.$": "$" },
        "Next": "ValidateOutput"
      },
      "ValidateOutput": {
        "Type": "Task",
        "Resource": "arn:aws:states:::lambda:invoke",
        "Parameters": { "FunctionName": "validate-output", "Payload.$": "$.Payload" },
        "End": true
      }
    }
  },
  "Next": "ComputePassRate"
}
```

Run the suite with `temperature` 0 (or several runs per case) so that results are comparable between versions.

## Iterative refinement beyond basic prompting

| Technique | What it changes | Example |
| --- | --- | --- |
| Structured input components | Separates instructions, context and data with labeled sections or XML-style tags, so the model does not confuse data with instructions | Instructions, then the contract text inside a delimited block, then the question |
| Output format specification | States the exact shape, fields, length and language of the answer; give an example | "Return a JSON object with `risk_level` (low, medium, high) and `reasons` (max 3 items)" |
| Few-shot examples | Shows 2–5 input-output pairs covering normal and edge cases | Classification of support tickets |
| Chain-of-thought instructions | Asks the model to reason step by step before the final answer, optionally in a separate section that the application strips | Multi-step calculations, policy eligibility |
| Role and audience | Sets expertise and register | "You are a claims adjuster writing to a customer" |
| Feedback loops | Collects failures (validator errors, low judge scores, user ratings), groups them, rewrites the prompt and re-runs the test suite | Weekly refinement cycle |
| Self-check | A second call reviews the first answer against the sources and rules | Regulated answers |

Bedrock Prompt Management can **optimize a prompt**: it rewrites a prompt for a chosen model, and you compare the original and the optimized versions before saving one as a version.

> **Exam trap.** Chain-of-thought improves reasoning but increases output tokens, cost and latency. When the requirement is "lowest latency" for a simple extraction, a clear output specification with few-shot examples is the better choice.

## Complex prompt systems with Amazon Bedrock Flows

Amazon Bedrock Flows links prompts, knowledge bases, Lambda functions and other AWS resources into a workflow that the application calls with `InvokeFlow`.

| Node | Role |
| --- | --- |
| Input / Output | Exactly one input node; one or more output nodes (for example one per branch) |
| Prompt | Runs a Prompt Management prompt or an inline prompt; inputs fill the variables, output is `modelCompletion` |
| Condition | Routes to different nodes according to ordered conditions (`==`, `!=`, `>`, `>=`, `and`, `or`, `not`); the first true condition wins, `default` otherwise |
| Iterator / Collector | Sends array items one by one (not in parallel) and gathers the results back into an array |
| DoWhile loop | Repeats nodes while a condition stays true (runs at least once) |
| Knowledge base | Queries a knowledge base, returns generated text or retrieval results |
| Lambda function | Pre-processing and post-processing: validation, enrichment, calls to business APIs |
| Inline code | Python run in an AWS-managed environment (preview) |
| S3 storage / S3 retrieval | Writes or reads an S3 object |
| Lex | Sends an utterance to an Amazon Lex bot and returns the predicted intent |
| Agent | Calls a Bedrock Agents alias |

Patterns:

- **Sequential chain**: extract fields, then classify, then draft the answer, each with its own focused prompt.
- **Conditional branching on model responses**: a classification prompt outputs `complaint` or `question`, and a Condition node routes to different prompts.
- **Reusable components**: the same managed prompt version is referenced by several flows.
- **Pre- and post-processing**: a Lambda node masks identifiers before the prompt and validates the output after it.

Deployment: the working draft has a test alias `TSTALIASID`; a **version** is an immutable snapshot; an **alias** points to a version and is what production calls, so rollback is re-pointing the alias.

> **Exam trap.** The Agent node calls Bedrock Agents, which became Agents Classic and has been closed to new customers since July 30, 2026. For a new design that needs an agent step, call an agent hosted on AgentCore Runtime from a Lambda node, or orchestrate with Step Functions.

## Key points

- Prompt Management: `{{variables}}`, `TEXT` or `CHAT`, up to 3 variants, immutable versions. Calling a prompt ARN forbids `system`, `inferenceConfig`, `toolConfig` and `additionalModelRequestFields` in the request: the managed prompt enforces them.
- Guardrails enforce rules that prompts cannot guarantee; structured outputs guarantee schema-valid JSON.
- Inference is stateless: store history in DynamoDB (TTL, 400 KB items) or AgentCore Memory; Comprehend custom classification for intent; Step Functions for clarification steps.
- Governance: draft, test, approve, version; CloudTrail for API activity, model invocation logging for prompt and response content, `requestMetadata` to tag invocations.
- QA: Lambda validators, Step Functions Map test harness, LLM-as-a-judge, CloudWatch metrics and alarms for regression.
- Refinement: structured inputs, explicit output format, few-shot, chain-of-thought (costs tokens), feedback loops, prompt optimization.
- Flows: Prompt, Condition, Iterator, Collector, DoWhile, Knowledge base, Lambda nodes; versions and aliases; avoid the Agent node for new designs (Agents Classic closed).
