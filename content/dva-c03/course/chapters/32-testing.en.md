DVA-C03 testing questions give you a serverless or container application and ask which command, test event, mock or environment lets you test it with the least effort: validate and unit-test the infrastructure code, invoke a function locally or in the cloud with a realistic JSON event, replace a missing dependency with a mock API, isolate test traffic with aliases, stages, tags or branches, and automate the repetitive part with AWS AI tools.

## Developing and validating tests with AWS SAM, AWS CDK and CloudFormation

Three layers of tests apply to an application defined as infrastructure as code:

| Layer | What it proves | AWS tools |
| --- | --- | --- |
| Template validation | The template is well formed and its resources and properties are valid | `sam validate --lint` (runs cfn-lint), `aws cloudformation validate-template`, `cdk synth` |
| Unit tests | The handler logic and the synthesized template behave as expected, with no AWS call | A test framework (pytest, Jest, JUnit) with mocked SDK clients; the CDK `assertions` module |
| Integration and end-to-end tests | The deployed resources work together (permissions, events, timeouts) | `sam remote invoke`, tests that call the deployed API or function, `sam sync --watch` for a development stack |

AWS SAM CLI commands the exam expects:

| Command | Use |
| --- | --- |
| `sam build` | Builds the functions and their dependencies into `.aws-sam/build` |
| `sam local invoke` | Runs one function once in a local container that emulates the Lambda runtime (Docker or a compatible container runtime required) |
| `sam local start-api` | Serves the API Gateway routes of the template on a local HTTP endpoint |
| `sam local start-lambda` | Exposes a local endpoint that emulates the Lambda Invoke API, so automated tests that use an AWS SDK can call local functions |
| `sam remote invoke` | Invokes a deployed Lambda function, or sends to a deployed Kinesis stream, SQS queue or Step Functions state machine |
| `sam sync --watch` | Pushes code changes to a development stack in the cloud as you save; not for production |

```bash
sam validate --lint
sam build
sam local invoke OrdersFunction --event events/order-created.json
sam local start-api
sam remote invoke OrdersFunction --stack-name orders-dev --event-file events/order-created.json
```

**CloudFormation**: `validate-template` only checks that the template is valid JSON or YAML with a correct structure; cfn-lint also checks resource types, property names and values against the resource specification. A **change set** previews what an update will add, modify or replace before you execute it.

**AWS CDK**: the `assertions` module tests the CloudFormation template synthesized from a stack, with Jest (TypeScript, JavaScript) or pytest (Python). **Fine-grained assertions** check specific resources and properties; **snapshot tests** compare the whole template with a stored baseline and catch any unintended change, but can fail after a CDK upgrade.

```python
# Python (pytest) - fine-grained assertions on a CDK stack
import aws_cdk as cdk
from aws_cdk.assertions import Template, Match
from app.orders_stack import OrdersStack

def test_orders_function():
    app = cdk.App()
    template = Template.from_stack(OrdersStack(app, "OrdersStack"))
    template.has_resource_properties("AWS::Lambda::Function", {
        "Runtime": "python3.12",
        "Timeout": 30,
    })
    template.resource_count_is("AWS::SQS::Queue", 2)
    template.has_resource_properties("AWS::SQS::Queue", {
        "RedrivePolicy": Match.object_like({"maxReceiveCount": 5}),
    })
```

`has_resource_properties` is a partial match: other properties may exist. `Match.object_equals` makes it strict, `Match.absent` asserts a property is missing.

> **Exam trap.** `aws cloudformation validate-template` passing does not mean the deployment will succeed: it does not check property values, quotas or permissions. "Catch invalid property values before deployment, with the LEAST effort" means cfn-lint (`sam validate --lint`); "verify that the stack defines a dead-letter queue" means a CDK fine-grained assertion, not a snapshot test.

## Mock APIs for external dependencies

When a front end or a partner team needs an API that does not exist yet, or when tests must not call a paid or unstable third-party service, return a canned response instead of the real back end.

An API Gateway REST API **mock integration** returns a response generated by API Gateway itself, with no back end and no Lambda function:

1. Create the method and choose the integration type `MOCK`.
2. In the **integration request**, a mapping template selects the status code.
3. In the **integration response**, a mapping template for that status returns the body; method responses declare the status codes and headers.

```bash
aws apigateway put-integration --rest-api-id a1b2c3d4e5 --resource-id r2d2c3 \
  --http-method GET --type MOCK \
  --request-templates '{"application/json": "{\"statusCode\": 200}"}'
```

```json
{
  "statusCode": 200,
  "orderId": "1234",
  "status": "SHIPPED"
}
```

The request template can contain logic (Velocity Template Language) to return 200 or 500 depending on a query string parameter, which lets tests exercise error paths. Mock integrations are not meant for large response templates; use a Lambda function if the fake response needs real logic. The CORS preflight `OPTIONS` method that the console creates is also a mock integration.

| Need | Solution |
| --- | --- |
| A front-end team must start before the back end exists | API Gateway mock integration on the planned resources and methods |
| Fake responses need computation or state | A stub Lambda function behind the same API |
| Unit tests must not call AWS | Stub the SDK client in the test (for example the botocore `Stubber` for boto3) |
| Swap the fake for the real back end later | Keep the same resource, method and model; replace only the integration and redeploy the stage |

> **Exam tip.** "Return a static sample response so that another team can develop against the API, with the LEAST operational overhead and no cost for compute" means an API Gateway mock integration, not a Lambda function or an EC2 stub server.

## Application test events for Lambda and API Gateway

A Lambda function receives a JSON event whose shape depends on the source. Tests must use that exact shape:

| Source | Shape of the event |
| --- | --- |
| API Gateway REST API, Lambda proxy integration | `httpMethod`, `path`, `pathParameters`, `queryStringParameters`, `headers`, `requestContext`, and `body` **as a string** (JSON must be parsed) |
| Amazon SQS | `Records` array; each record has `messageId`, `receiptHandle` and `body` as a string |
| Amazon S3 | `Records` array; `s3.bucket.name` and `s3.object.key` (URL-encoded) |
| Amazon EventBridge | `source`, `detail-type` and the payload in `detail` |

Ways to create and run test events:

| Tool | Detail |
| --- | --- |
| Lambda console **private** test event | Visible only to its creator, no extra permission, up to 10 per function |
| Lambda console **shareable** test event | Visible to users of the same account; stored as a schema in the EventBridge schema registry `lambda-testevent-schemas`, which needs EventBridge schemas permissions |
| `sam local generate-event` | Prints a sample event for a service (`s3 put`, `sqs receive-message`, `apigateway aws-proxy`...), with options such as `--bucket` |
| `sam remote invoke --test-event-name` | Invokes the deployed function with a shareable test event |
| `aws lambda invoke` | Invokes a deployed function or alias with a payload file |
| API Gateway console **Test** | Calls the method with a path, query string, headers and body and shows the request, the response and the execution log |

```bash
sam local generate-event s3 put --bucket uploads-dev --key photos/cat.jpg > events/s3-put.json
sam local invoke ThumbnailFunction --event events/s3-put.json

aws lambda invoke --function-name orders:dev \
  --cli-binary-format raw-in-base64-out \
  --payload file://events/order-created.json response.json
```

```json
{
  "httpMethod": "POST",
  "path": "/orders",
  "pathParameters": null,
  "queryStringParameters": { "dryRun": "true" },
  "headers": { "Content-Type": "application/json" },
  "body": "{\"customerId\": \"c-42\", \"items\": [{\"sku\": \"A1\", \"qty\": 2}]}"
}
```

> **Exam trap.** With AWS CLI version 2, a raw JSON payload fails or is misread unless you add `--cli-binary-format raw-in-base64-out` (the default expects base64). And in a proxy event, `body` is a string: `event["body"]["customerId"]` fails, the handler must parse it first.

Deleting a function does not delete its shareable test event schemas; they must be removed from the schema registry.

## Creating and configuring application environments

Each environment (development, test, staging, production) must receive its own code version and configuration without copying the whole application.

**Lambda versions and aliases.** Publishing a version freezes the code and configuration (immutable, with its own ARN ending in `:3`); `$LATEST` stays editable. An **alias** (`dev`, `test`, `prod`) is a named pointer to a version that callers and event sources use; moving the alias changes the version without changing any caller. A **weighted alias** routes a percentage of traffic to a second published version.

```bash
aws lambda publish-version --function-name orders --description "commit 9f3c2e1"
aws lambda update-alias --function-name orders --name prod --function-version 7 \
  --routing-config '{"AdditionalVersionWeights": {"8": 0.1}}'
```

**API Gateway stages and stage variables.** A stage (`dev`, `prod`) is a named deployment snapshot with its own URL (`https://a1b2c3d4e5.execute-api.eu-west-1.amazonaws.com/prod`), settings (throttling, caching, logging) and **stage variables**. Pointing the Lambda integration at an alias through a stage variable lets each stage call its own alias; each alias then needs a resource-based permission allowing API Gateway to invoke it.

```text
arn:aws:lambda:eu-west-1:111122223333:function:orders:${stageVariables.lambdaAlias}
```

**Container image tags.** Tag each build with an immutable identifier (Git commit SHA, semantic version) and deploy that tag or the image digest to each environment; promote the same image from test to production instead of rebuilding it. Turn on **tag immutability** in the Amazon ECR repository so that a tag such as `1.4.0` can never be overwritten; a mutable `latest` tag makes environments drift.

**AWS Amplify branches.** Each connected Git branch of an Amplify app is deployed as its own environment with its own URL (for example `main` for production, `dev` for testing). **Pull request previews** deploy every pull request to a unique preview URL, and for full-stack apps with private repositories a temporary back end that is deleted when the pull request closes. Previews count toward the quota of 50 branches per app, and are restricted on public repositories for security.

**AWS Copilot environments.** Copilot CLI grouped the shared resources of an environment (VPC, cluster, load balancer) for ECS services. **AWS Copilot CLI reached end of support on June 12, 2026**: no new features or security updates. Never choose it for a new project; migrate to Amazon ECS Express Mode, AWS CDK L3 constructs (`ApplicationLoadBalancedFargateService`) or the CloudFormation stacks Copilot generated.

| Requirement | Answer |
| --- | --- |
| Callers must not change when a new function version goes to production | Invoke through an alias and move the alias |
| Each API stage must call a different function version | Stage variable in the integration ARN + aliases + invoke permission per alias |
| The tested image must be exactly the one deployed to production | Immutable ECR tags or image digest, promoted between environments |
| Reviewers must see each pull request of a web app before merging | Amplify pull request previews |

> **Exam trap.** An alias can't point to `$LATEST` for weighted routing, and a published version can't be edited: to change code or configuration, update `$LATEST`, publish a new version and move the alias.

## Using AWS AI tools to generate and automate tests

**Kiro** is the AWS agentic development tool (IDE and CLI) built on Amazon Bedrock. **Amazon Q Developer closed to new sign-ups on May 15, 2026, and Kiro is its successor**: do not choose Q Developer for a new team.

| Testing task | Kiro feature |
| --- | --- |
| Generate tests from requirements | A **spec**: `requirements.md` (user stories and acceptance criteria), `design.md`, `tasks.md`; tests derive from the acceptance criteria |
| Apply the team's test conventions every time | **Steering** files in `.kiro/steering/` (framework, naming, coverage target, mocking rules) |
| Write or update tests automatically when code changes | **Agent hooks** in `.kiro/hooks/`: triggers such as File Create, File Save, File Delete or Post Task Execution run a shell command or an agent prompt |
| Run tests and analyze results in CI/CD without a person | **Kiro CLI headless mode**: `kiro-cli chat --no-interactive` with an API key in `KIRO_API_KEY` |

Automate the repetitive workflow in AWS CodeBuild: run the unit and regression tests on every commit, publish the results as **test reports** (JUnit XML, NUnit, TestNG, Cucumber JSON, Visual Studio TRX) and **code coverage reports**, and let the AI summarize failures. Test reports expire after 30 days unless exported to Amazon S3.

```yaml
version: 0.2
env:
  secrets-manager:
    KIRO_API_KEY: ci/kiro:api-key
phases:
  install:
    commands:
      - pip install -r requirements-dev.txt
      - curl -fsSL https://cli.kiro.dev/install | bash
  build:
    commands:
      - pytest --junitxml=reports/junit.xml --cov=src --cov-report=xml:reports/coverage.xml
  post_build:
    commands:
      - kiro-cli chat --v3 --no-interactive --trust-tools=read_file,grep_search "Summarize the failed tests in reports/junit.xml and list the untested functions in src/"
reports:
  unit-tests:
    files:
      - junit.xml
    base-directory: reports
    file-format: JUNITXML
  coverage:
    files:
      - coverage.xml
    base-directory: reports
    file-format: COBERTURAXML
```

Good practice the exam rewards:

- AI-generated tests are code: review them, run them, and keep a **deterministic** pass/fail gate (the test run's exit code), not the AI's opinion.
- Store the API key in AWS Secrets Manager and grant only the tools needed (`--trust-tools=...`) rather than `--trust-all-tools`.
- Generate synthetic test data (for example with an Amazon Bedrock model) instead of copying production data that contains PII.

> **Exam tip.** "Generate unit tests automatically each time a developer creates a new source file" means a Kiro agent hook with a File Create trigger. "Run the AI test analysis in the pipeline with no interactive session" means Kiro CLI headless mode in a CodeBuild step.

## Key points

- `sam validate --lint` (cfn-lint) catches invalid properties; `validate-template` checks syntax only; change sets preview updates.
- `sam local invoke` and `start-api` test locally in a container; `sam remote invoke` tests the deployed function; `sam sync --watch` is for development stacks only.
- CDK `assertions`: fine-grained assertions for specific resources, snapshot tests for unintended changes.
- API Gateway mock integration: canned responses with no back end, status chosen by the request mapping template.
- Test events follow the source's shape; proxy `body` is a string; shareable test events live in the `lambda-testevent-schemas` registry; CLI v2 needs `--cli-binary-format raw-in-base64-out`.
- Environments: Lambda aliases and versions, API Gateway stages and stage variables, immutable ECR tags, Amplify branches and pull request previews. Copilot CLI is out of support since June 12, 2026.
- Kiro (successor of Amazon Q Developer): specs, steering, agent hooks, headless CLI in CodeBuild; CodeBuild test and coverage reports keep the deterministic gate.
